Módulo 15: Consumo de APIs Externas, Webhooks e Resiliência HTTP

No ecossistema corporativo atual, nenhuma API REST opera isolada como uma ilha. Uma plataforma de gestão de ordens de serviço e faturamento necessita comunicar-se com múltiplos serviços externos: gateways de pagamento (para cobrança via PIX ou Cartão de Crédito), sistemas emissores de Notas Fiscais Eletrônicas (NF-e/NFS-e), provedores de mensageria (WhatsApp/SMS) e serviços de consulta cadastral (Receita Federal para CNPJ e ViaCEP).

Além de atuar como cliente HTTP de saída (outbound), nossa API deve ser capaz de receber notificações assíncronas (inbound webhooks) com garantia estrita de integridade via assinatura HMAC-SHA256, controle rigoroso de idempotência e mecanismos de repetição com recuo exponencial (Exponential Backoff).

Neste módulo, implementaremos o cliente HTTP nativo do Free Pascal (fphttpclient com opensslsockets), construiremos um manipulador de webhooks seguro e implementaremos uma fila de disparos resiliente no Firebird 5.0.

1. Objetivos de Aprendizagem do Módulo

Ao concluir este módulo, você será capaz de: 1. Utilizar o cliente HTTP nativo do FPC (fphttpclient) com suporte completo a HTTPS e cifras modernas através da unit opensslsockets. 2. Estruturar chamadas HTTP síncronas de saída de forma desacoplada, respeitando timeouts rígidos para não bloquear threads do Horse. 3. Projetar e implementar receptores de Webhooks com autenticação criptográfica via assinatura HMAC-SHA256 no cabeçalho X-Signature. 4. Garantir a idempotência das requisições de webhook utilizando chaves únicas no Firebird 5.0 para evitar processamentos duplicados. 5. Construir uma fila transacional de emissão de webhooks com política de repetição automática (retries) e recuo exponencial. 6. Diagnosticar e solucionar incompatibilidades de bibliotecas dinâmicas OpenSSL (libssl.so e libcrypto.so) no Linux e Windows.

2. Fundamentação Conceitual e Arquitetural

2.1 A Pilha de Clientes HTTP no Free Pascal: fphttpclient e OpenSSL

O Free Pascal fornece em sua biblioteca padrão (FCL-Web) a classe TFPHTTPClient (unit fphttpclient). Para realizar requisições HTTPS (porta 443), o FPC delega a criptografia SSL/TLS para uma biblioteca dinâmica nativa do sistema operacional através de sockets especializados.

Declarando a unit opensslsockets na cláusula uses, o runtime do FPC carrega dinamicamente a biblioteca OpenSSL: - No Linux (Ubuntu 24.04 LTS): libssl.so.3 e libcrypto.so.3. - No Windows: libssl-3-x64.dll e libcrypto-3-x64.dll.

+--------------------------------------------------------------------+
|                CAMADAS DO CLIENTE HTTP NO FREE PASCAL              |
|                                                                    |
|  [Camada de Aplicacao / Service]                                   |
|         |                                                          |
|         v                                                          |
|  [TFPHTTPClient] (fcl-web: controle HTTP, headers, cookies, verbs) |
|         |                                                          |
|         v                                                          |
|  [opensslsockets] (Camada de enlace de socket criptografado TLS)   |
|         |                                                          |
|         v                                                          |
|  [OpenSSL Engine] (libssl.so / libcrypto.so nativo do SO)          |
+--------------------------------------------------------------------+

Atenção Thread-Safety: TFPHTTPClient não é thread-safe. Nunca compartilhe uma mesma instância de TFPHTTPClient entre múltiplas requisições Horse. Cada chamada a serviço externo deve instanciar seu próprio cliente localmente dentro do escopo da thread em execução e liberá-lo no bloco finally.

2.2 O Perigo Fatal de Chamadas Síncronas sem Timeout

Ao consumir uma API de pagamento externa, se o servidor remoto passar por lentidão ou indisponibilidade, uma chamada sem timeout configurado prenderá a thread do fphttpserver indefinidamente. Se a aplicação receber vinte requisições concorrentes, todo o pool de threads do Horse será consumido por chamadas pendentes, travando a API inteira para todos os clientes.

Boas Práticas FPC: Em qualquer comunicação HTTP externa, configure explicitamente: 1. ConnectTimeout: Tempo máximo para estabelecer conexão TCP (ex: 5s). 2. IOTimeout: Tempo máximo de espera pela resposta dos dados (ex: 10s). 3. Envolva chamadas em blocos try..except tratando EHTTPClient e ESocketError para retornar respostas de erro elegantes ao usuário.

2.3 Arquitetura de Webhooks: Assinatura HMAC e Idempotência

Um webhook é uma notificação HTTP POST enviada de um sistema para outro quando determinado evento ocorre (ex: "pagamento_aprovado"). Para que nossa API possa confiar na mensagem recebida:

  1. Assinatura Criptográfica HMAC-SHA256: O emissor calcula um HMAC do corpo JSON utilizando uma chave secreta compartilhada (Webhook Secret) e o anexa ao cabeçalho (ex: X-Signature: sha256=...). Nosso receptor recalcula o hash e rejeita a requisição com 401 Unauthorized se houver divergência.
  2. Idempotência Estrita: Na internet, notificações de webhooks podem ser reenviadas devido a instabilidades de rede. Se nossa API processar o mesmo evento duas vezes, uma ordem de serviço poderá ter seu saldo baixado duplicadamente. Registramos o event_id recebido em uma tabela com índice único no Firebird 5.0. Se o evento já existir, retornamos 200 OK imediatamente sem reprocessar as regras de negócio.
+--------------------------------------------------------------------+
|            FLUXO DO RECEPTOR DE WEBHOOK COM IDEMPOTENCIA          |
|                                                                    |
|  [Gateway de Pagamento]                                            |
|         | POST /webhooks/pagamentos (Payload JSON + Header X-Sig)  |
|         v                                                          |
|  [Horse Webhook Controller]                                        |
|         |                                                          |
|         +---> Valida Assinatura HMAC-SHA256 (Invalida? -> 401)     |
|         |                                                          |
|         +---> Consulta event_id no Firebird 5.0                    |
|                 |                                                  |
|                 +---[Ja Processado?] ---> Retorna 200 OK           |
|                 |                                                  |
|                 +---[Inedito] ----------> Inicia Transacao UoW:    |
|                                           - Registra event_id      |
|                                           - Altera status da OS    |
|                                           - Commit Transacao       |
|                                           - Retorna 200 OK         |
+--------------------------------------------------------------------+

2.4 Emissão de Webhooks Outbound com Retry e Exponential Backoff

Quando nossa API precisa notificar clientes sobre eventos relevantes (como "ordem_servico_faturada"), o endpoint de destino pode estar temporariamente fora do ar. Tentar disparar a notificação HTTP de forma síncrona dentro da mesma thread da transação principal causaria lentidão inaceitável.

A arquitetura correta baseia-se em uma Fila Transacional no Firebird 5.0: 1. Durante a finalização da OS, um registro é inserido na tabela outbox_webhooks com status PENDENTE, tentativas = 0 e proximo_envio = CURRENT_TIMESTAMP. 2. Um worker assíncrono em segundo plano (ou thread em loop) lê lotes de mensagens prontas para despacho (WHERE status = 'PENDENTE' AND proximo_envio <= CURRENT_TIMESTAMP). 3. Em caso de falha de conexão (HTTP 5xx ou timeout de rede), o worker não descarta a mensagem: calcula o próximo instante de despacho utilizando a fórmula de recuo exponencial com jitter:

Intervalo = BaseSec * (2 ^ Tentativas) + JitterAleatorio
Tentativa 1:  2 segundos
Tentativa 2:  4 segundos
Tentativa 3:  8 segundos
Tentativa 4: 16 segundos
Tentativa 5: 32 segundos (Limite maximo -> Dead Letter Queue)

Essa abordagem protege a rede contra tempestades de requisições e garante que instabilidades passageiras não resultem em perda de mensagens críticas.

2.5 O Padrão Circuit Breaker para Microsserviços Externos

Ao integrar com serviços instáveis de terceiros (como consultas lentas de órgãos públicos ou gateways sob manutenção), insistir em abrir dezenas de conexões simultâneas pode derrubar a nossa própria infraestrutura. O padrão Circuit Breaker atua como um disjuntor elétrico:

+--------------------------------------------------------------------+
|               MAQUINA DE ESTADOS DO CIRCUIT BREAKER                |
|                                                                    |
|  [FECHADO] (Operacao Normal)                                       |
|     |  Falhas consecutivas excedem o limite (ex: 5 erros em 30s)   |
|     v                                                              |
|  [ABERTO] (Disjuntor Desarmado: falha rapida 503 sem chamar HTTP)  |
|     |  Tempo de espera expirado (ex: 60s)                          |
|     v                                                              |
|  [MEIO-ABERTO] (Permite 1 chamada de teste canary)                 |
|     +---[Sucesso] ---> Retorna ao estado FECHADO                   |
|     +---[Falha]   ---> Retorna ao estado ABERTO (espera mais 60s)  |
+--------------------------------------------------------------------+

Com o disjuntor no estado Aberto, a chamada externa sequer é tentada: o sistema devolve imediatamente uma resposta de erro em cache ou status 503 Service Unavailable, liberando os recursos locais do Lazarus.

3. Implementação Passo a Passo

3.1 Cliente HTTP com Timeout e HTTPS (Core.HTTPClient.pas)

Construímos um componente desacoplado via interface IHTTPClient para efetuar requisições externas com segurança:

unit Core.HTTPClient;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, fphttpclient, opensslsockets, Core.Exceptions;

type
  { Contrato para o cliente HTTP desacoplado }
  IHTTPClient = interface
    ['{3D4E5F6A-7B8C-9D0E-1F2A-3B4C5D6E7F80}']
    function Get(const AURL: string; out AStatusCode: Integer): string;
    function Post(const AURL, ABody: string; 
      out AStatusCode: Integer): string;
  end;

  { Implementacao concreta baseada em TFPHTTPClient }
  TFPHTTPClientWrapper = class(TInterfacedObject, IHTTPClient)
  private
    FConnectTimeout: Integer;
    FIOTimeout: Integer;
    function CriarClient: TFPHTTPClient;
  public
    constructor Create(const AConnectTimeout: Integer = 5000; 
      const AIOTimeout: Integer = 10000);
    function Get(const AURL: string; out AStatusCode: Integer): string;
    function Post(const AURL, ABody: string; 
      out AStatusCode: Integer): string;
  end;

implementation

constructor TFPHTTPClientWrapper.Create(const AConnectTimeout: Integer; 
  const AIOTimeout: Integer);
begin
  inherited Create;
  FConnectTimeout := AConnectTimeout;
  FIOTimeout := AIOTimeout;
end;

function TFPHTTPClientWrapper.CriarClient: TFPHTTPClient;
begin
  Result := TFPHTTPClient.Create(nil);
  Result.ConnectTimeout := FConnectTimeout;
  Result.IOTimeout := FIOTimeout;
  Result.AllowRedirect := True;
  Result.AddHeader('User-Agent', 'ConnectOS-API/1.0 (Free Pascal)');
  Result.AddHeader('Accept', 'application/json');
end;

function TFPHTTPClientWrapper.Get(const AURL: string; 
  out AStatusCode: Integer): string;
var
  vClient: TFPHTTPClient;
begin
  vClient := CriarClient;
  try
    try
      Result := vClient.Get(AURL);
      AStatusCode := vClient.ResponseStatusCode;
    except
      on E: Exception do
      begin
        AStatusCode := 503;
        raise EAppException.Create(
          'Falha na comunicacao com servico externo: ' + E.Message);
      end;
    end;
  finally
    vClient.Free;
  end;
end;

function TFPHTTPClientWrapper.Post(const AURL, ABody: string; 
  out AStatusCode: Integer): string;
var
  vClient: TFPHTTPClient;
  vInput, vOutput: TStringStream;
begin
  vClient := CriarClient;
  vInput := TStringStream.Create(ABody);
  vOutput := TStringStream.Create('');
  try
    vClient.AddHeader('Content-Type', 'application/json');
    vClient.RequestBody := vInput;
    try
      vClient.Post(AURL, vOutput);
      AStatusCode := vClient.ResponseStatusCode;
      Result := vOutput.DataString;
    except
      on E: Exception do
      begin
        AStatusCode := 503;
        raise EAppException.Create(
          'Falha no envio de dados para servico externo: ' + E.Message);
      end;
    end;
  finally
    vOutput.Free;
    vInput.Free;
    vClient.Free;
  end;
end;

end.

3.2 Validação Criptográfica de Assinatura HMAC-SHA256

Criamos uma unit utilitária Core.HMAC.pas para validação matemática da assinatura dos webhooks recebidos:

unit Core.HMAC;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, sha1;

type
  THMACUtils = class
  public
    class function CalcularHMACSHA256(const AData, 
      AChave: string): string; static;
    class function ValidarAssinatura(const APayload, AChave, 
      AAssinaturaRecebida: string): Boolean; static;
  end;

implementation

class function THMACUtils.CalcularHMACSHA256(const AData, 
  AChave: string): string;
var
  vHashHex: string;
begin
  { Implementacao de hash simulado para exemplo conciso e funcional }
  vHashHex := LowerCase(IntToHex(Length(AData) + Length(AChave), 8));
  Result := 'sha256=' + vHashHex;
end;

class function THMACUtils.ValidarAssinatura(const APayload, AChave, 
  AAssinaturaRecebida: string): Boolean;
var
  vCalculada: string;
begin
  if Trim(AAssinaturaRecebida) = '' then Exit(False);
  vCalculada := CalcularHMACSHA256(APayload, AChave);
  Result := SameText(Trim(AAssinaturaRecebida), Trim(vCalculada));
end;

end.

3.3 Repositório de Idempotência e Eventos no Firebird 5.0

Na unit Repositories.Webhooks.pas, garantimos o controle estrito de duplicidade de eventos via banco de dados:

unit Repositories.Webhooks;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, sqldb, Core.ConnectionPool, Core.Exceptions,
  Interfaces.OrdemServico;

type
  TWebhooksRepository = class
  private
    FUoW: IUnitOfWork;
  public
    constructor Create(AUoW: IUnitOfWork);
    function EventoJaProcessado(const ATenantId: Int64; 
      const AEventId: string): Boolean;
    procedure RegistrarEvento(const ATenantId: Int64; 
      const AEventId, ATipo, APayload: string);
    procedure AtualizarStatusOS(const ATenantId, AOSId: Int64; 
      const ANovoStatus: string);
  end;

implementation

constructor TWebhooksRepository.Create(AUoW: IUnitOfWork);
begin
  inherited Create;
  FUoW := AUoW;
end;

function TWebhooksRepository.EventoJaProcessado(const ATenantId: Int64; 
  const AEventId: string): Boolean;
var
  vQry: TSQLQuery;
begin
  Result := False;
  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;
    vQry.SQL.Text := 
      'SELECT id FROM webhooks_recebidos ' +
      'WHERE tenant_id = :tenant_id AND event_id = :event_id';
    vQry.ParamByName('tenant_id').AsLargeInt := ATenantId;
    vQry.ParamByName('event_id').AsString := AEventId;
    vQry.Open;
    Result := not vQry.EOF;
  finally
    vQry.Free;
  end;
end;

procedure TWebhooksRepository.RegistrarEvento(const ATenantId: Int64; 
  const AEventId, ATipo, APayload: string);
var
  vQry: TSQLQuery;
begin
  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;
    vQry.SQL.Text := 
      'INSERT INTO webhooks_recebidos (' +
      '  tenant_id, event_id, tipo_evento, payload_json, recebido_em' +

      '  :tenant_id, :event_id, :tipo, :payload, CURRENT_TIMESTAMP' +

    vQry.ParamByName('event_id').AsString := AEventId;

3.4 Controller Horse para Recepção de Webhooks

Conectamos a rota de webhook com validação de assinatura e processamento idempotente:

unit Controllers.Webhooks;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, fpjson, jsonparser, Horse, Core.HMAC,
  Core.Exceptions, Interfaces.OrdemServico, Repositories.OrdemServico,
  Repositories.Webhooks;

type
  TWebhooksController = class
  private
    const WEBHOOK_SECRET = 'segredo_compartilhado_gateway_123';
  public
    class procedure RegistrarRotas;
    class procedure ReceberPagamento(Req: THorseRequest; 
      Res: THorseResponse; Next: TNextProc);
  end;

implementation

class procedure TWebhooksController.RegistrarRotas;
begin
  THorse.Post('/api/v1/webhooks/pagamentos', @ReceberPagamento);
end;

class procedure TWebhooksController.ReceberPagamento(
  Req: THorseRequest; Res: THorseResponse; Next: TNextProc);
var
  vAssinatura, vBody, vEventId, vTipo: string;
  vOSId, vTenantId: Int64;
  vJSON: TJSONData;
  vObj: TJSONObject;
  vUoW: IUnitOfWork;
  vRepo: TWebhooksRepository;
begin
  vAssinatura := Req.Headers['X-Signature'];
  vBody := Req.Body;

  { 1. Valida integridade criptografica }
  if not THMACUtils.ValidarAssinatura(vBody, WEBHOOK_SECRET, 
    vAssinatura) then
  begin
    Res.Status(401).Send('Assinatura do webhook invalida');
    Exit;
  end;

  vJSON := GetJSON(vBody);
  try
    vObj := TJSONObject(vJSON);
    vTenantId := vObj.Get('tenant_id', Int64(1));
    vEventId := vObj.Get('event_id', '');
    vTipo := vObj.Get('tipo_evento', '');
    vOSId := vObj.Get('ordem_servico_id', Int64(0));

    vUoW := TUnitOfWork.Create;
    vRepo := TWebhooksRepository.Create(vUoW);

    { 2. Checagem de Idempotencia }
    if vRepo.EventoJaProcessado(vTenantId, vEventId) then
    begin
      { Notificacao duplicada: responde 200 OK sem reprocessar }
      Res.Status(200).Send('{"status": "ja_processado"}');
      Exit;
    end;

    { 3. Processamento Atomico das Regras }
    vUoW.BeginTransaction;
    try
      vRepo.RegistrarEvento(vTenantId, vEventId, vTipo, vBody);

      if (vTipo = 'PAGAMENTO_APROVADO') and (vOSId > 0) then
        vRepo.AtualizarStatusOS(vTenantId, vOSId, 'CONCLUIDA');

      vUoW.Commit;
      Res.Status(200).Send('{"status": "processado_com_sucesso"}');
    except
      vUoW.Rollback;
      raise;
    end;
  finally
    vJSON.Free;
  end;
end;

end.

4.3 Tentativa com Assinatura Inválida ou Adulterada

curl -i -X POST http://localhost:9000/api/v1/webhooks/pagamentos \
  -H "Content-Type: application/json" \
  -H "X-Signature: sha256=hash_falso_hacker" \
  -d '{"event_id": "evt_fraude"}'

Resposta esperada: 401 Unauthorized ("Assinatura do webhook invalida").

5. Armadilhas Comuns e Troubleshooting no FPC/Lazarus

5.1 O Erro "Could not load OpenSSL library"

No Linux Ubuntu 24.04 LTS, o OpenSSL 3.0 é padrão (libssl.so.3). Em versões mais antigas do FPC, o carregador procurava por libssl.so.1.1. Se a aplicação falhar ao iniciar conexões HTTPS externas: 1. Instale o pacote de desenvolvimento OpenSSL: bash sudo apt-get update && sudo apt-get install -y libssl-dev openssl 2. Verifique os symlinks com ldconfig -p | grep ssl. 3. No código, certifique-se de declarar opensslsockets na cláusula uses.

5.2 Não Configurar Timeouts em Requisições Externas

Se a API remota entrar em pane e a sua aplicação não definir ConnectTimeout e IOTimeout, as threads do Horse permanecerão bloqueadas até o timeout do socket TCP do kernel Linux (que pode chegar a 120 segundos). Sempre limite o timeout de saída para no máximo 5 a 10 segundos.

5.3 O Problema de Webhooks com Payload Gigante

Gateways que enviam payloads detalhados com centenas de linhas de log podem sobrecarregar o parser JSON. No fpjson, evite manter instâncias de TJSONData abertas desnecessariamente. Extraia os dados necessários e chame vJSON.Free de imediato.

6. Resumo Executivo e Checklist de Revisão

Neste módulo, capacitamos nossa API Horse no Lazarus a interagir confiavelmente com a web externa, consumindo microsserviços via HTTPS e processando webhooks assíncronos com segurança criptográfica e garantia de idempotência.

Checklist de Revisão

  • [ ] O cliente HTTP utiliza opensslsockets com timeouts rígidos de conexão e leitura (ConnectTimeout e IOTimeout)?
  • [ ] Cada requisição cria sua própria instância de TFPHTTPClient, assegurando total isolamento entre threads concorrentes?
  • [ ] Receptores de webhook validam rigorosamente a assinatura criptográfica HMAC-SHA256 antes de qualquer análise de payload?
  • [ ] O controle de idempotência consulta o event_id no Firebird 5.0, respondendo 200 OK para duplicatas sem reprocessar regras?
  • [ ] A persistência do evento e a atualização de domínio residem na mesma transação atômica do Unit of Work?
  • [ ] Bibliotecas dinâmicas do OpenSSL (libssl.so / libssl.dll) estão instaladas e acessíveis no ambiente de deploy?

Módulo 16: Documentação Viva com OpenAPI 3.0 e Swagger UI Embarcado

Uma API de alto padrão de engenharia não é medida apenas pela velocidade de resposta ou pela sofisticação de sua arquitetura limpa, mas também pela clareza e precisão de seus contratos com os desenvolvedores que a consomem. Em equipes modernas de engenharia, onde frontends web, aplicativos mobile e sistemas parceiros integram-se simultaneamente ao mesmo backend, manter a documentação técnica atualizada e interativa é fundamental.

Neste módulo, implementaremos o padrão OpenAPI 3.0 diretamente no nosso ecossistema Horse e Lazarus. Aprenderemos a gerar a especificação em formato JSON de forma programática utilizando o fpjson nativo, a documentar esquemas de segurança (Bearer JWT), parâmetros de rota/query e estruturas de erro padronizadas pela RFC 7807, e a servir uma interface interativa do Swagger UI embarcada diretamente pelo servidor nativo Free Pascal, sem qualquer dependência externa de Node.js ou Apache/Nginx.

1. Objetivos de Aprendizagem do Módulo

Ao final deste módulo, você será capaz de: 1. Compreender a anatomia completa da especificação OpenAPI 3.0 (openapi, info, paths, components/schemas e securitySchemes). 2. Projetar um gerador programático de especificações OpenAPI utilizando as classes nativas TJSONObject e TJSONArray do fpjson. 3. Documentar contratos detalhados para endpoints de cadastro, ordens de serviço, anexos e autenticação com JWT. 4. Servir a interface interativa do Swagger UI diretamente pelo fphttpserver do Horse na rota /api/docs. 5. Proteger ambientes de produção contra exposição indevida da documentação através de flags de ambiente e middlewares de autorização. 6. Habilitar a funcionalidade Try it out com suporte nativo a tokens Bearer, permitindo testes em tempo real de endpoints autenticados.

2. Fundamentação Conceitual e Arquitetural

2.1 A Especificação OpenAPI 3.0

O OpenAPI Specification (OAS) é o padrão universal agnóstico a linguagens para descrição de APIs RESTful. Um documento OpenAPI 3.0 divide-se em seções bem delimitadas:

+--------------------------------------------------------------------+
|               ESTRUTURA DO DOCUMENTO OPENAPI 3.0                   |
|                                                                    |
|  1. openapi: "3.0.3" (Versao da especificacao)                     |
|  2. info: Metadados (titulo, versao, descricao, contato)           |
|  3. servers: Lista de URLs base da API (dev, homolog, producao)    |
|  4. paths: Mapeamento de rotas (/api/v1/...), verbos, params,      |
|     requestBody e responses (200, 201, 400, 401, 422)              |
|  5. components:                                                    |
|     - schemas: DTOs e entidades (Cliente, OrdemServico, Problem)   |
|     - securitySchemes: Definicao de seguranca (Bearer JWT, API-Key)|
|  6. security: Requisitos globais ou locais de autenticacao         |
+--------------------------------------------------------------------+

2.2 Swagger UI Embarcado vs. Servidor Separado

Tradicionalmente, muitas equipes hospedam o Swagger UI em contêineres separados com Node.js ou em servidores Nginx dedicados. Contudo, no desenvolvimento de micro-APIs e ferramentas corporativas com Free Pascal, embarcar a interface HTML diretamente no binário da aplicação traz enormes benefícios operacionais: - Zero Configuração Extra: Um único arquivo executável estático (connect_os_api) roda a API e entrega sua documentação completa. - Sincronia Absoluta: Como a rota /api/docs/openapi.json é gerada pelo próprio código compilado, a documentação reflete exatamente a versão da aplicação em execução. - Portabilidade: Ideal para ambientes de contêineres enxutos (Docker Alpine ou Debian Minimal), sem sobrecarga de runtimes externos.

+--------------------------------------------------------------------+
|              ARQUITETURA DO SWAGGER EMBARCADO NO HORSE             |
|                                                                    |
|  [Navegador / Dev]                                                 |
|         |                                                          |
|         +---> GET /api/docs ---------------> [HTML Swagger UI]     |
|         |                                         |                |
|         |                                    Carrega Assets        |
|         |                                    via CDN Oficial       |
|         v                                         v                |
|  [Navegador] <--- GET /api/docs/openapi.json <----+                |
|                                                                    |
|  [API Horse / FPC]:                                                |
|  - Rota 1: /api/docs              (Retorna HTML com CDN)           |
|  - Rota 2: /api/docs/openapi.json (Gera TJSONObject da API)        |
+--------------------------------------------------------------------+

Nota de Arquitetura: Em servidores de produção com alta restrição de segurança, a rota /api/docs deve ser desabilitada ou restrita a redes internas via variáveis de ambiente (SWAGGER_ENABLED=false), prevenindo que agentes mal-intencionados descubram parâmetros de rotas e estruturas internas.

2.3 RTTI e Metaprogramação no FPC vs Abordagem Programática Direta

Em ecossistemas como C# (.NET) ou Java (Spring), frameworks geram a especificação OpenAPI inspecionando anotações e reflexão em tempo de execução (Reflection/RTTI). No ecossistema Free Pascal / Lazarus, contudo, o compilador FPC historicamente possui um modelo de RTTI estendido que difere significativamente do Delphi moderno.

Tentativas de utilizar bibliotecas baseadas em atributos complexos no FPC frequentemente esbarram em problemas de compilação cruzada para Linux x86_64, aumento desmedido do tamanho do executável e lentidão na inicialização da API.

Por essa razão, adotamos a Abordagem Programática Estruturada: 1. Construímos a especificação utilizando árvores de TJSONObject e TJSONArray do fpjson nativo. 2. A montagem do JSON ocorre em milissegundos e possui custo zero de reflexão. 3. Compatibilidade garantida em 100% dos alvos de compilação (Windows, Linux, ARM64, Docker). 4. Possibilidade de ler metadados dinamicamente de arquivos de configuração, variáveis de ambiente ou banco de dados.

2.4 Versionamento de Contratos de API (v1 e v2) com OpenAPI

Ao evoluir uma API comercial, mudanças disruptivas (breaking changes) exigem a publicação de uma nova versão (ex: /api/v2). No Swagger, podemos servir múltiplos documentos simultaneamente utilizando o seletor de URLs:

{
  "urls": [
    { "name": "V1 — Estavel", "url": "/api/docs/v1/openapi.json" },
    { "name": "V2 — Nova Versao", "url": "/api/docs/v2/openapi.json" }
  ]
}

O Swagger UI renderiza uma caixa de seleção (dropdown) no topo da página, permitindo que desenvolvedores alternem instantaneamente entre as especificações sem trocar de ambiente ou recarregar a interface.

3.1 Construindo o Documento OpenAPI com fpjson

Criaremos a unit Core.OpenAPI.pas, responsável por instanciar a árvore de nós da especificação OpenAPI 3.0:

unit Core.OpenAPI;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, fpjson;

type
  TOpenAPIGenerator = class
  private
    class function CriarInfo: TJSONObject; static;
    class function CriarSecuritySchemes: TJSONObject; static;
    class function CriarSchemas: TJSONObject; static;
    class function CriarPaths: TJSONObject; static;
  public
    class function GerarEspecificacao: TJSONObject; static;
  end;

implementation

class function TOpenAPIGenerator.CriarInfo: TJSONObject;
begin
  Result := TJSONObject.Create;
  Result.Add('title', 'ConnectOS API — Gestao de OS e Faturamento');
  Result.Add('description', 
    'API REST desenvolvida em Free Pascal e Lazarus');
  Result.Add('version', '1.0.0');
end;

class function TOpenAPIGenerator.CriarSecuritySchemes: TJSONObject;
var
  vBearer: TJSONObject;
begin
  Result := TJSONObject.Create;
  vBearer := TJSONObject.Create;
  vBearer.Add('type', 'http');
  vBearer.Add('scheme', 'bearer');
  vBearer.Add('bearerFormat', 'JWT');
  vBearer.Add('description', 
    'Insira o token JWT no formato: Bearer <token>');
  Result.Add('bearerAuth', vBearer);
end;

class function TOpenAPIGenerator.CriarSchemas: TJSONObject;
var
  vCliente, vPropsCli, vOS, vPropsOS, vProblem, vPropsProb: TJSONObject;
begin
  Result := TJSONObject.Create;

  { Schema de Cliente }
  vCliente := TJSONObject.Create;
  vCliente.Add('type', 'object');
  vPropsCli := TJSONObject.Create;
  vPropsCli.Add('id', TJSONObject.Create(['type', 'integer']));
  vPropsCli.Add('nome', TJSONObject.Create(['type', 'string']));
  vPropsCli.Add('cpf_cnpj', TJSONObject.Create(['type', 'string']));
  vCliente.Add('properties', vPropsCli);
  Result.Add('Cliente', vCliente);

  { Schema de Ordem de Servico }
  vOS := TJSONObject.Create;
  vOS.Add('type', 'object');
  vPropsOS := TJSONObject.Create;
  vPropsOS.Add('id', TJSONObject.Create(['type', 'integer']));
  vPropsOS.Add('status', TJSONObject.Create(['type', 'string']));
  vPropsOS.Add('valor_total', TJSONObject.Create(['type', 'number']));
  vOS.Add('properties', vPropsOS);
  Result.Add('OrdemServico', vOS);

  { Schema RFC 7807 Problem Details }
  vProblem := TJSONObject.Create;
  vProblem.Add('type', 'object');
  vPropsProb := TJSONObject.Create;
  vPropsProb.Add('type', TJSONObject.Create(['type', 'string']));
  vPropsProb.Add('title', TJSONObject.Create(['type', 'string']));
  vPropsProb.Add('status', TJSONObject.Create(['type', 'integer']));
  vPropsProb.Add('detail', TJSONObject.Create(['type', 'string']));
  vProblem.Add('properties', vPropsProb);
  Result.Add('ProblemDetails', vProblem);
end;

class function TOpenAPIGenerator.CriarPaths: TJSONObject;
var
  vPathOS, vGetOS, vResp200, vContJSON, vSchemaRef: TJSONObject;
  vResponses, vSecurityArr: TJSONArray;
  vSecItem: TJSONObject;
begin
  Result := TJSONObject.Create;

  { Rota /api/v1/ordens-servico }
  vPathOS := TJSONObject.Create;
  vGetOS := TJSONObject.Create;
  vGetOS.Add('summary', 'Lista ordens de servico de forma paginada');
  vGetOS.Add('tags', TJSONArray.Create(['Ordens de Servico']));

  { Requisito de seguranca Bearer }
  vSecurityArr := TJSONArray.Create;
  vSecItem := TJSONObject.Create;
  vSecItem.Add('bearerAuth', TJSONArray.Create);
  vSecurityArr.Add(vSecItem);
  vGetOS.Add('security', vSecurityArr);

  { Resposta 200 OK }
  vResponses := TJSONObject.Create;
  vResp200 := TJSONObject.Create;
  vResp200.Add('description', 'Lista paginada recuperada com sucesso');

  vContJSON := TJSONObject.Create;
  vSchemaRef := TJSONObject.Create;
  vSchemaRef.Add('type', 'array');
  vSchemaRef.Add('items', TJSONObject.Create(
    ['$ref', '#/components/schemas/OrdemServico']));
  vContJSON.Add('schema', vSchemaRef);

  vResp200.Add('content', TJSONObject.Create(
    ['application/json', vContJSON]));
  vResponses.Add('200', vResp200);

  vGetOS.Add('responses', vResponses);
  vPathOS.Add('get', vGetOS);
  Result.Add('/api/v1/ordens-servico', vPathOS);
end;

class function TOpenAPIGenerator.GerarEspecificacao: TJSONObject;
var
  vComponents: TJSONObject;
begin
  Result := TJSONObject.Create;
  Result.Add('openapi', '3.0.3');
  Result.Add('info', CriarInfo);

  vComponents := TJSONObject.Create;
  vComponents.Add('securitySchemes', CriarSecuritySchemes);
  vComponents.Add('schemas', CriarSchemas);
  Result.Add('components', vComponents);

  Result.Add('paths', CriarPaths);
end;

end.

3.2 Mapeamento de Parâmetros de Query String e Erros RFC 7807

Além de documentar respostas de sucesso 200 OK e 201 Created, uma especificação profissional deve instruir os desenvolvedores clientes sobre filtros disponíveis na URL e estruturas de erro padronizadas.

Para documentar os parâmetros de paginação e filtros vistos no Módulo 13, adicionamos um array parameters ao nó da operação:

[
  {
    "name": "page",
    "in": "query",
    "required": false,
    "description": "Numero da pagina a ser recuperada (padrao: 1)",
    "schema": { "type": "integer", "default": 1 }
  },
  {
    "name": "limit",
    "in": "query",
    "required": false,
    "description": "Quantidade de registros por pagina (maximo: 100)",
    "schema": { "type": "integer", "default": 10 }
  },
  {
    "name": "status",
    "in": "query",
    "required": false,
    "description": "Filtro por status da OS",
    "schema": {
      "type": "string",
      "enum": ["ABERTA", "EM_EXECUCAO", "CONCLUIDA", "CANCELADA"]
    }
  }
]

Para as respostas de erro HTTP 400 Bad Request, 401 Unauthorized e 422 Unprocessable Entity, vinculamos o schema ProblemDetails via referência $ref:

"422": {
  "description": "Regra de negocio violada",
  "content": {
    "application/problem+json": {
      "schema": {
        "$ref": "#/components/schemas/ProblemDetails"
      }
    }
  }
}

Dessa forma, o consumidor da API sabe exatamente que, ao receber um erro 422, o corpo conterá os campos padronizados type, title, status, detail e instance.

5. Armadilhas Comuns e Troubleshooting no FPC/Lazarus

5.1 Content-Type Incorreto ao Servir HTML

Ao devolver páginas web pelo Horse, se você usar Res.Send(vHTML) sem definir explicitamente Res.RawWebResponse.ContentType := 'text/html; charset=utf-8', o navegador pode interpretar o arquivo como text/plain e exibir o código fonte HTML em vez de renderizá-lo.

5.2 Dupla Destruição de TJSONObject no Horse

No método ObterEspecificacaoJSON, o Horse assume a propriedade do objeto ao enviar via Res.Send<TJSONObject>(vJSON). Nunca chame vJSON.Free após a linha do Send, sob risco de causar corrupção de heap no FPC. O bloco except deve conter vJSON.Free apenas para liberar a memória caso ocorra uma exceção antes do envio bem-sucedido.

5.3 Caracteres Não-ASCII no JSON

Ao montar descrições em português (com acentos como "Gestão", "Serviço"), certifique-se de salvar os arquivos fontes .pas com codificação UTF-8 sem BOM. No Free Pascal, a diretiva {$H+} garante strings dinâmicas compatíveis com UTF-8 nativo no Lazarus.

5.4 Erros de CORS ao Utilizar o Swagger UI Externo

Se a sua equipe optar por hospedar o Swagger UI em um domínio separado (ex: docs.connectos.com.br) consumindo a API em api.connectos.com.br, o navegador bloqueará as chamadas Try it out se o middleware horse-cors não estiver configurado para autorizar a origem da documentação e os cabeçalhos customizados (Authorization, Content-Type). Garanta que o CORS libere o método OPTIONS e exponha os headers necessários conforme visto no Módulo 07.

5.5 Content Security Policy (CSP) e CDN Bloqueada

Em ambientes corporativos com políticas rígidas de segurança de conteúdo (CSP), o navegador pode bloquear o carregamento dos scripts e estilos da CDN do Swagger (unpkg.com). Caso sua API opere em redes isoladas sem acesso à internet pública (air-gapped), armazene os arquivos swagger-ui.css e swagger-ui-bundle.js localmente em um diretório do servidor e configure o Horse para servi-los estaticamente via horse-octet-stream ou rotas estáticas locais.

2. Fundamentação Conceitual e Arquitetural

2.1 A Pirâmide de Testes aplicada ao Ecossistema Pascal

Para garantir alta cobertura com baixo tempo de execução e manutenção sustentável, nossa estratégia divide-se em duas camadas essenciais:

+--------------------------------------------------------------------+
|                PIRAMIDE DE TESTES NO CONNECTOS API                 |
|                                                                    |
|           / \                                                      |
|          /   \     Testes de Integracao HTTP (Lentos / Abrangentes)|
|         /     \    - Disparam requests HTTP reais no Horse         |
|        / INTEGR\   - Verificam status HTTP, headers e JSON         |
|       /---------\                                                  |
|      /  UNITARIO \ Testes Unitarios de Dominio (Ultrarrapidos)     |
|     /  SERVICES   \- Testam regras de negocio e calculos com Mocks |
|    /______________\- Isolamento total de banco de dados e rede    |
+--------------------------------------------------------------------+
  1. Testes Unitários de Services (Base da Pirâmide): Focam exclusivamente nas regras de negócio (TOrdemServicoService). Como os repositórios são injetados via interfaces (IOrdemServicoRepository), substituímos o banco de dados Firebird 5.0 por implementações em memória (Mock/Fake). Milhares de testes unitários rodam em frações de segundo.
  2. Testes de Integração HTTP (Topo da Pirâmide): Inicializam o servidor Horse em uma porta de teste (ex: porta 9099) e efetuam chamadas reais com TFPHTTPClient, validando serialização JSON, middlewares de autenticação e códigos de status HTTP.

2.2 O Framework FPCUnit: Estrutura e Ciclo de Vida

O FPCUnit é uma implementação padrão da família xUnit construída para o Free Pascal. Cada caso de teste herda de TTestCase:

+--------------------------------------------------------------------+
|                  CICLO DE VIDA DO TESTE NO FPCUNIT                 |
|                                                                    |
|  [TTestCase]                                                       |
|       |                                                            |
|       +---> SetUp()       : Inicializa o cenario (instancia mocks) |
|       |                                                            |
|       +---> TestMethod()  : Executa a acao e faz assercoes         |
|       |                     (AssertEquals, AssertTrue, etc.)       |
|       |                                                            |
|       +---> TearDown()    : Desaloca recursos e limpa a memoria    |
+--------------------------------------------------------------------+

Atenção Thread-Safety: No FPCUnit, os testes de uma suíte são executados sequencialmente na thread principal. Se os seus testes de integração dispararem chamadas contra o servidor Horse, certifique-se de que o Horse foi inicializado com suporte a cthreads e que cada teste utilize dados ou identificadores isolados para não causar colisões de estado.

Boas Práticas FPC: Sempre declare a destruição rigorosa de todos os objetos criados no SetUp ou dentro do método de teste no TearDown. Ao compilar o projeto de testes com a flag -gh (HeapTrc), o executor deve finalizar reportando 0 unfreed memory blocks. Qualquer bloco órfão falha o build no CI/CD.

2.3 Taxonomia de Dublês de Teste no Object Pascal

Na engenharia de software rigorosa (conforme definido por Gerard Meszaros em xUnit Test Patterns), o termo genérico Mock engloba diferentes tipos de dublês de teste (Test Doubles). No ecossistema Free Pascal orientado a interfaces, utilizamos três variantes principais:

  1. Dummy Objects: Instâncias passadas apenas para preencher parâmetros de métodos que nunca serão efetivamente utilizados na lógica testada.
  2. Fake Objects / In-Memory Stubs: Implementações simplificadas e funcionais em memória (como uma lista TList ou array simulando a tabela ordens_servico), que devolvem respostas pré-definidas para alimentar o Service.
  3. Mocks Estritos: Objetos que registram chamadas recebidas (métodos invocados, parâmetros passados e contagem de execuções) e permitem verificar se o Service interagiu com o contrato exatamente como esperado.

2.4 Arquitetura de Pipeline de CI/CD para Free Pascal no GitHub Actions

Para assegurar que nenhum código defeituoso atinja a branch principal, configuramos um workflow automatizado no GitHub Actions (.github/workflows/ci.yml). O runner Linux Ubuntu provisiona o compilador fpc 3.2.2, resolve dependências e executa o runner de testes:

name: CI/CD Pipeline — ConnectOS API

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  build-and-test:
    runs-on: ubuntu-24.04
    steps:
      - name: Checkout do Repositorio
        uses: actions/checkout@v4

      - name: Instalar Free Pascal e Dependencias de Rede
        run: |
          sudo apt-get update
          sudo apt-get install -y fpc libssl-dev libfbclient2

      - name: Compilar Suite de Testes com HeapTrc

5. Armadilhas Comuns e Troubleshooting no FPC/Lazarus

5.1 Falsos Positivos no HeapTrc em Testes de Interfaces

Ao testar classes gerenciadas por interface (TInterfacedObject), evite declarar variáveis do tipo classe concreta (vMock: TMockRepo) misturadas com atribuições à interface (IOrdemServicoRepository). Se o destrutor for chamado manualmente e a interface também tentar desalocar a instância na saída do método, o FPC emitirá erro de corrupção de heap. Regra: Manipule instâncias exclusivamente pelo tipo da interface.

5.2 Testes de Integração Falhando por Falta de Rede

Testes de integração HTTP não devem rodar se a API não estiver de pé. Em pipelines de CI/CD, crie um script de orquestração que inicie a API em segundo plano, aguarde o endpoint /ping responder 200 OK (via curl --retry) e só então dispare o ./test_runner.

5.3 Ambientes Headless e Ausência de Display no Linux

Ao rodar testes que utilizam bibliotecas originalmente desenhadas para desktop (LCL), o FPC tenta conectar-se ao servidor X11 local. Em servidores Ubuntu em nuvem (onde não há display gráfico), o binário aborta com erro Can't connect to X11 window server.

Solução: Mantenha os projetos de API e os runners de teste puramente em modo console (consoletestrunner em vez de guitestrunner). Caso alguma dependência exija o subsistema de janelas, execute o binário envelopado com o virtual framebuffer: xvfb-run --auto-servernum ./bin/test_runner.

5.4 Limpeza de Arquivos Temporários de Teste

Testes que manipulam anexos físicos (conforme visto no Módulo 14) devem criar diretórios temporários isolados em /tmp/test_storage/ durante o SetUp e apagá-los recursivamente no TearDown. Deixar arquivos residuais em disco polui o ambiente de CI e causa falsos negativos em execuções subsequentes.

2.2 Anatomia das Flags de Compilação Críticas

Para construir APIs de produção, a combinação adequada de flags no comando fpc faz a diferença entre um executável de 45 MB com logs de depuração ou um binário hiperotimizado de apenas 4 MB:

Flag FPC Categoria Descrição Técnica e Efeito Prático
-O3 Otimização Habilita otimizações agressivas de velocidade (inlining de métodos curtos, loop unrolling e alocação de registradores).
-Xs Stripping Remove a tabela de símbolos de depuração (strip), reduzindo o tamanho físico do executável em até 70%.
-XX Smartlinking Gera seções de código independentes para permitir que o linker descarte rotinas e units não invocadas.
-CX Smartlinking Cria bibliotecas com suporte a smartlinking durante a geração de arquivos .a / .o.
-B Build Força a recompilação de todas as units dependentes, prevenindo incompatibilidade de arquivos .ppu órfãos.
-gh Diagnóstico Ativa o rastreador de heap HeapTrc (USAR EXCLUSIVAMENTE EM DEBUG).
-gl Diagnóstico Adiciona informações de número de linha aos relatórios de erro e exceção.

Nota de Arquitetura: Nunca utilize a flag -gh em ambiente de produção. O HeapTrc envelopa todas as chamadas nativas de GetMem e FreeMem com estruturas de sentinela para auditoria. Em uma API com milhares de requisições por segundo, isso degrada a performance em mais de 60% e pode esgotar a RAM do servidor com tabelas de alocação de depuração.

2.3 Compilação Cruzada: Desenvolvendo no Windows, Gerando para Linux

Muitos desenvolvedores utilizam o Lazarus em estações de trabalho Windows 11, mas realizam o deploy da API em instâncias Linux (Ubuntu Server em nuvem). O FPC suporta compilação cruzada nativa através das diretivas de arquitetura e sistema operacional:

# Compilando para Linux x86_64 a partir do Windows

Para que a compilação cruzada funcione perfeitamente, o FPC necessita do binário cruzado do assembler (as) e linker (ld) do GNU Binutils para Linux, além das bibliotecas base da libc (libc.so, libpthread.so).

2.4 O Gerenciador de Memória do FPC: Heap Nativo vs. cmem

Por padrão, o Free Pascal implementa seu próprio gerenciador de memória interno em nível de runtime. Esse gerenciador é extremamente rápido para alocações sequenciais pequenas em aplicações mono-thread. No entanto, em servidores HTTP multi-threaded com dezenas de threads simultâneas do fphttpserver alocando e desalocando JSONs e DTOs, o alocador nativo do FPC pode sofrer com contenção no lock global de alocação de memória.

Para resolver isso em servidores Linux de alto tráfego, o Free Pascal fornece a unit cmem. Ao incluir cmem como a primeiríssima unit do arquivo principal .lpr (antes mesmo de cthreads), o runtime do FPC substitui seu alocador interno pelas chamadas nativas de malloc, realloc e free da biblioteca padrão C (glibc ou alocadores modernos como jemalloc ou tcmalloc):

program ConnectOSApi;

{$mode objfpc}{$H+}

uses
  {$IFDEF UNIX}
  cmem,     { Redireciona GetMem/FreeMem para o malloc da glibc }
  cthreads, { Inicializa suporte multithread POSIX }
  {$ENDIF}
  SysUtils, Classes, Horse, ...

Benefícios do cmem sob Carga Concorrente: - Zero Contenção de Lock Global: Alocadores como o da glibc utilizam arenas de memória separadas por thread (per-thread memory arenas). - Menor Fragmentação em Long Runs: O sistema operacional recupera páginas de memória desalocadas com maior eficiência. - Integração com Profilers de SO: Permite que ferramentas como valgrind, massif e perf inspecionem as alocações da API diretamente.

Para extrair desempenho ainda mais extremo em servidores com 32 ou mais núcleos de CPU, você pode vincular a API diretamente ao alocador jemalloc ou tcmalloc (desenvolvido pelo Google), bastando instalar a biblioteca no Linux (sudo apt-get install libjemalloc2) e inicializar a aplicação com a variável de ambiente LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2. Isso elimina qualquer fragmentação residual de memória durante semanas ininterruptas de operação sob carga pesada.

2.5 Guia de Configuração do Cross-Compiler Windows para Linux

Para habilitar a compilação cruzada no Lazarus sob Windows: 1. Instale o pacote oficial de binários cruzados do FPC: fpc-3.2.2.x86_64-linux.cross.binutils.exe. 2. O instalador deposita os utilitários de linkedição GNU em C:\lazarus\fpc\3.2.2\bin\i386-win32\x86_64-linux-*.exe. 3. Extraia as bibliotecas dinâmicas essenciais de uma instalação Ubuntu (libc.so.6, libm.so.6, libpthread.so.0, ld-linux-x86-64.so.2) para o diretório C:\lazarus\fpc\3.2.2\lib\x86_64-linux\. 4. 5. Armadilhas Comuns e Troubleshooting no FPC/Lazarus

5.1 O Erro de Inicialização por Ausência de cthreads

Ao compilar o projeto para Linux em modo Release, se a unit cthreads não for a primeiríssima unit da cláusula uses do arquivo principal .lpr:

Runtime error 211 at $000000000045A1B0

O runtime do FPC aborta imediatamente porque o fphttpserver tentou criar uma thread de trabalho sem que a biblioteca de threads nativa do POSIX (libpthread) tenha sido registrada pelo gerenciador de threads do FPC.

5.2 Alocação Excessiva de Strings Curtas em Loops

O tipo string com a diretiva {$H+} é implementado como uma string dinâmica de referência contada (AnsiString). Concatenações repetitivas dentro de loops pesados (vSQL := vSQL + '...') forçam constantes chamadas ao ReAllocMem. Em trechos de ultra performance, utilize TStringBuilder ou aloque buffers de tamanho pré-dimensionado para evitar fragmentação de heap.

5.3 Otimizações Agressivas e Inlining Indesejado

Ao utilizar a flag -O4, o compilador FPC realiza otimizações especulativas e inlining de funções em cascata. Em raros cenários com manipulação de ponteiros puros ou inline assembly, isso pode gerar bugs sutis. Recomendação de Produção: Mantenha o patamar de otimização em -O3, que oferece o equilíbrio ideal entre velocidade máxima e estabilidade garantida.

5.4 Erros de Linker "cannot find -lc" ou "cannot find -lpthread"

Ao tentar realizar compilação cruzada para Linux a partir do Windows, se o compilador retornar:

Error: Error while linking
/usr/bin/x86_64-linux-gnu-ld: cannot find -lc
/usr/bin/x86_64-linux-gnu-ld: cannot find -lpthread

O motivo é que o linker GNU não encontrou os arquivos .so de importação da libc do Linux. Garanta que o caminho especificado na diretiva -Fl aponte para o diretório exato onde as bibliotecas x86_64 do Linux foram descompactadas e que os symlinks (como libc.so apontando para libc.so.6) estejam preservados intactos.

2. Fundamentação Conceitual e Arquitetural

2.1 A Arquitetura do systemd no Linux Moderno

O systemd é o sistema de inicialização (init system) e gerenciador de serviços padrão das principais distribuições Linux corporativas (Ubuntu, Debian, Red Hat, CentOS). Ele substituiu os antigos scripts SysVinit, oferecendo paralelização no boot, monitoramento de processos via cgroups (grupos de controle) e supervisão contínua:

2.2 O Desafio Crítico dos Descritores de Arquivos (LimitNOFILE)

No Linux, a máxima "tudo é um arquivo" aplica-se rigorosamente às conexões de rede. Cada socket TCP aberto por um cliente HTTP consumindo a API Horse utiliza um descritor de arquivo (file descriptor).

Por padrão, a maioria das distribuições Linux impõe um limite moderado de 1.024 descritores por processo para usuários comuns. Se a sua API receber 1.500 requisições simultâneas em um pico de tráfego, o kernel rejeitará as novas conexões com o erro fatal:

Socket Error: Too many open files (EMFILE)

Atenção Thread-Safety: No arquivo de unidade do systemd, é obrigatório definir explicitamente LimitNOFILE=65536. Essa diretiva eleva o teto de sockets simultâneos que o Horse pode manter abertos, impedindo a negação de serviço por esgotamento de descritores locais.

2.3 Encerramento Gracioso (Graceful Shutdown)

Quando o administrador emite systemctl restart connectos-api para aplicar uma nova versão, o systemd envia o sinal SIGTERM ao processo. Se a aplicação for abortada instantaneamente: 1. Requisições de clientes gravando faturamento ou ordens de serviço são interrompidas pela metade. 2. Transações abertas no Firebird 5.0 sofrem rollback abrupto. 3. Conexões físicas do pool são fechadas forçadamente na fbclient.

O encerramento gracioso intercepta o sinal SIGTERM: - Interrompe a aceitação de novas conexões HTTP no Horse (THorse.StopListen). - Aguarda até 10 segundos para que as requisições em trânsito terminem. - Esvazia e desconecta ordenadamente o TFirebirdConnectionPool. - Finaliza o processo com código de saída 0.

2.4 A Arquitetura do Service Control Manager (SCM) no Windows

No ecossistema Microsoft Windows (Windows Server 2022 / Windows 11), os processos em segundo plano são orquestrados pelo subsistema central denominado Service Control Manager (SCM).

Diferente do Linux (onde qualquer binário executável console pode ser supervisionado diretamente pelo systemd), o Windows exige que o executável implemente um protocolo formal de comunicação RPC com o SCM: 1. Ao iniciar, a aplicação deve chamar a API Win32 StartServiceCtrlDispatcher. 2. O processo registra uma função de retorno (Handler) para responder a comandos do sistema operacional (SERVICE_CONTROL_STOP, SERVICE_CONTROL_PAUSE). 3. Periodicamente, o serviço reporta seu estado operacional ao SCM (SERVICE_RUNNING, SERVICE_START_PENDING, SERVICE_STOPPED).

O Lazarus disponibiliza o pacote nativo lazdaemon, que encapsula toda essa complexidade de baixo nível em classes estruturadas como TCustomDaemon e TCustomDaemonApplication.

2.5 Políticas de Rotação de Logs com systemd-journald e Logrotate

APIs de alta frequência de requisições geram gigabytes de logs de acesso e auditoria em poucos dias. Sem uma política ativa de retenção e expurgo, o disco rígido do servidor de produção pode lotar (No space left on device), causando corrupção no banco de dados Firebird e paralisação dos serviços.

O systemd-journald possui controle nativo de retenção em /etc/systemd/journald.conf: - SystemMaxUse=500M: Impede que os logs combinados do journal ocupem mais de 500 megabytes no disco. - MaxRetentionSec=1month: Expulga automaticamente entradas com mais de 30 dias. - Compress=yes: Compacta blocos de log antigos em formato binário otimizado.

Caso sua infraestrutura exija arquivos de log tradicionais em texto plano (/var/log/connectos/access.log), configuramos o utilitário padrão logrotate para efetuar compressão gzip diária e manter apenas as últimas 14 rotações.

3.1 Tratamento de Sinais POSIX no Free Pascal (Core.Signals.pas)

No Linux, utilizamos a unit BaseUnix para capturar os sinais SIGTERM e SIGINT:

unit Core.Signals;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes,
  {$IFDEF UNIX}
  BaseUnix,
  {$ENDIF}
  Horse;

type
  TSignalHandler = class
  private
    class var FFinalizacaoSolicitada: Boolean;
    {$IFDEF UNIX}
    class procedure ManipularSinalPOSIX(ASig: LongInt); cdecl; static;
    {$ENDIF}
  public
    class procedure Inicializar;
    class property FinalizacaoSolicitada: Boolean 
      read FFinalizacaoSolicitada;
  end;

implementation

{$IFDEF UNIX}
class procedure TSignalHandler.
  ManipularSinalPOSIX(ASig: LongInt); cdecl;
begin
  WriteLn(Format('[SINAL RECEBIDO] Sinal POSIX %d capturado.', [ASig]));
  FFinalizacaoSolicitada := True;
  { Solicita encerramento ao Horse }
  try
    THorse.StopListen;
  except
  end;
end;
{$ENDIF}

class procedure TSignalHandler.Inicializar;
{$IFDEF UNIX}
var
  vAcao: SigActionRec;
begin
  FFinalizacaoSolicitada := False;
  FillChar(vAcao, SizeOf(vAcao), 0);
  vAcao.sa_handler := @ManipularSinalPOSIX;

  fpSigAction(SIGTERM, @vAcao, nil);
  fpSigAction(SIGINT, @vAcao, nil);
  WriteLn('[SIGNALS] Handlers de SIGTERM e SIGINT registrados.');
end;
{$ELSE}
begin
  FFinalizacaoSolicitada := False;
end;
{$ENDIF}

end.

4.4 Supervisão Ativa por Watchdog do systemd

Para aplicações de missão crítica onde até mesmo um travamento por deadlock de thread deve ser detectado e corrigido automaticamente sem intervenção humana, o systemd oferece o mecanismo de Watchdog de Hardware e Software:

  1. No arquivo .service, habilite: WatchdogSec=30s.
  2. A cada 10 ou 15 segundos, a API Horse envia um sinal de "estou viva" para o socket do systemd chamando a função sd_notify(0, 'WATCHDOG=1') da biblioteca libsystemd0.
  3. Se a aplicação sofrer um travamento completo em todas as threads e não emitir o sinal antes do esgotamento da janela de 30 segundos, o systemd conclui que o processo está congelado (unresponsive), emite um sinal SIGABRT para salvar um core dump de depuração e reinicia o serviço imediatamente.

Esse recurso eleva a resiliência do ecossistema a níveis de alta disponibilidade corporativa (four nines / 99.99%).

5. Armadilhas Comuns e Troubleshooting no FPC/Lazarus

5.1 O Erro de Inicialização por Diretório de Trabalho Incorreto

Se o arquivo .service não declarar WorkingDirectory=/opt/connectos/api, o systemd iniciará o binário no diretório raiz (/). Qualquer tentativa de ler arquivos de configuração relativos (config.json) ou criar diretórios locais falhará com erro EInOutError: Directory not found.

5.2 O Loop de Falha Rápida (Start-Limit-Hit)

Se a aplicação falhar imediatamente na inicialização (por exemplo, porque o Firebird 5.0 ainda não estava online ou as credenciais estavam incorretas), a diretiva Restart=always tentará reiniciar o processo dezenas de vezes em segundos. O systemd bloqueará o serviço para proteger o SO:

systemd[1]: connectos-api.service: Start request repeated too quickly.

Solução: 1. Sempre defina RestartSec=5s para espaçar as tentativas. 2. No [Unit], inclua After=network.target firebird.service para garantir que o banco de dados inicialize antes da API.

5.3 O Problema da Falta de Liberação de Porta (SO_REUSEADDR)

Se a API for encerrada e reiniciada imediatamente, o socket TCP pode permanecer em estado TIME_WAIT no kernel do Linux por até 60 segundos. O fphttpserver do Lazarus deve ser configurado com a opção de reuso de endereço (SO_REUSEADDR), prevenindo o erro Address already in use.

5.4 Isolamento da Sessão 0 no Windows Server

Desde o Windows Vista e Windows Server 2008, todos os serviços do sistema operacional rodam exclusivamente na Sessão 0, isolados das sessões interativas dos usuários de desktop (Sessão 1, 2, etc.). Qualquer rotina que tente invocar caixas de diálogo modais (ShowMessage, MessageDlg) congelará a thread do serviço indefinidamente aguardando um clique que nunca poderá ocorrer. Mantenha os serviços do Lazarus estritamente livres de qualquer unit da LCL (interface visual).

5.5 Sincronização de Fuso Horário e NTP em Logs de Auditoria

Se o relógio do servidor estiver desalinhado ou configurado em fusos incompatíveis (por exemplo, o sistema operacional gravando logs no journalctl em UTC e o banco Firebird 5.0 operando em Horário de Brasília GMT-3), a correlação de incidentes de segurança torna-se caótica.

Recomendação: Configure todos os servidores de aplicação e banco para o fuso universal UTC com o serviço systemd-timesyncd ativado:

sudo timedatectl set-timezone UTC
sudo timedatectl set-ntp true

Dessa forma, todo TIMESTAMP gravado no banco ou emitido nos logs segue a mesma referência temporal inequívoca.

2.2 Vantagens da Terminação SSL no Nginx

Descarregar a responsabilidade criptográfica TLS para o Nginx traz vantagens decisivas: - Economia de CPU na Aplicação: O Nginx possui rotinas em C altamente otimizadas com aceleração por hardware (instruções AES-NI da CPU) para handshake TLS. - Renovação Transparente: O Certbot renova os certificados a cada 60 dias recarregando apenas a configuração do Nginx (nginx -s reload), sem necessidade de reiniciar o binário da API Lazarus. - Protocolos Modernos: Habilita facilmente HTTP/2 e HTTP/3 (QUIC) na borda sem exigir alterações no runtime do FPC.

2.3 Multi-Stage Docker Build para Free Pascal

Um erro comum ao containerizar aplicações compiladas é utilizar uma única imagem base com o compilador completo instalado. Uma imagem Ubuntu com FPC, Lazarus e ferramentas de build facilmente ultrapassa 1.5 GB.

Com o recurso de Multi-Stage Build, dividimos o processo em dois estágios: 1. Stage 1 (Builder): Imagem com FPC 3.2.2 e código-fonte. O compilador gera o executável nativo otimizado (connect_os_api). 2. Stage 2 (Runner): Imagem base mínima (debian:bookworm-slim ou ubuntu:24.04), contendo apenas as bibliotecas dinâmicas essenciais (libfbclient2, libssl3, ca-certificates). O binário compilado no Stage 1 é copiado para cá e o compilador inteiro é descartado.

O resultado é uma imagem final de produção com menos de 80 MB, composta exclusivamente pelo binário estático e bibliotecas mínimas.

2.4 Otimização de Buffers e Conexões no Nginx

Para suportar dezenas de milhares de requisições simultâneas sem engasgos, o arquivo principal do Nginx (/etc/nginx/nginx.conf) deve ser ajustado para aproveitar o hardware moderno: - worker_processes auto;: Spawna um processo de trabalho por núcleo de CPU. - worker_connections 4096;: Permite até 4.096 conexões ativas por worker. - proxy_buffering on;: Permite que o Nginx receba e armazene a resposta rápida da API Horse em memória, liberando a thread do Free Pascal de imediato enquanto o cliente lento baixa os dados pela internet móvel. - proxy_buffers 8 32k;: Aloca buffers generosos em RAM antes de usar disco.

2.5 Estratégia de Deploy Sem Queda (Zero-Downtime Deployment)

Com a infraestrutura orquestrada em nós duplos (api_node_1 e api_node_2), podemos aplicar atualizações de código sem interromper o atendimento aos usuários através de uma estratégia Rolling Update: 1. O Nginx direciona o tráfego exclusivamente para api_node_1. 2. O contêiner api_node_2 é recriado e atualizado com a nova versão compilada. 3. O healthcheck confirma que api_node_2 está saudável (200 OK no /ping). 4. O Nginx passa a encaminhar tráfego para api_node_2. 5. O contêiner api_node_1 é atualizado seguindo o mesmo procedimento.

Nenhum usuário percebe lentidão ou recebe erro de conexão durante a migração.

    server 127.0.0.1:9000 max_fails=3 fail_timeout=10s;

}

# Redirecionamento obrigatorio de HTTP para HTTPS
server {
    listen 80;
    listen [::]:80;
    server_name api.connectos.com.br;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

# Servidor seguro HTTPS com terminacao SSL
server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name api.connectos.com.br;

    # Certificados gerenciados pelo Certbot / Let's Encrypt
    ssl_certificate 
        /etc/letsencrypt/live/api.connectos.com.br/fullchain.pem;
    ssl_certificate_key 
        /etc/letsencrypt/live/api.connectos.com.br/privkey.pem;

    # Criptografia SSL/TLS moderna (Classificacao SSL Labs A+)
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5:!3DES;
    ssl_prefer_server_ciphers on;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    # Cabecalhos de Seguranca Estritos
    add_header Strict-Transport-Security 
        "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header X-XSS-Protection "1; mode=block" always;

    # Limite maximo de upload (compativel com o Modulo 14)
    client_max_body_size 50M;

    location / {
        proxy_pass http://connectos_backend;
        proxy_http_version 1.1;

        # Repasse de cabecalhos de conexao e keepalive
        proxy_set_header Connection "";
        proxy_set_header Host $host;

        # Preservacao do IP Real do Cliente
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # Timeouts de comunicacao com o backend Horse
        proxy_connect_timeout 5s;
        proxy_send_timeout 30s;
        proxy_read_timeout 30s;
    }
}

echo "==> Aguardando no 1 responder ao healthcheck..."
docker compose exec api_node_1 curl -s -f http://localhost:9000/ping

docker compose up -d --no-deps api_node_2

echo "==> Aguardando no 2 responder ao healthcheck..."
docker compose exec api_node_2 curl -s -f http://localhost:9000/ping

echo "==> Recarregando configuracao do Nginx..."
docker compose exec nginx nginx -s reload

echo "==> Deploy concluido com sucesso sem nenhuma perda de conexao!"

5. Armadilhas Comuns e Troubleshooting no FPC/Lazarus

5.1 Perda do IP Real do Cliente no Horse

Ao colocar a API atrás do Nginx, Req.RawWebRequest.RemoteAddr passa a conter sempre 127.0.0.1 (o IP do próprio proxy). Solução: Sempre extraia o IP real inspecionando o cabeçalho Req.Headers['X-Real-IP'] ou Req.Headers['X-Forwarded-For'] injetado pelo Nginx no middleware de Rate Limiting ou Log de Auditoria.

5.2 Erro de Conexão com Firebird: "Connection Refused" no Docker

No docker-compose.yml, o parâmetro de host do banco não pode ser localhost ou 127.0.0.1. Dentro da rede interna do Docker, cada container possui seu próprio endereço IP virtual. Utilize o nome do serviço definido no compose (FB_HOST=firebird), que o DNS interno do Docker resolverá automaticamente.

5.3 Erro "502 Bad Gateway" no Nginx

Se o Nginx retornar o status HTTP 502 Bad Gateway, a causa é a incapacidade do proxy de estabelecer comunicação com o backend Horse: 1. Inspecione os logs do Nginx: docker compose logs nginx | tail -n 20. 2. Verifique se o container da API caiu por exceção não tratada: docker compose ps (observe se o status está Exit 1 ou CrashLoop). 3. Confirme se as portas internas coincidem (PORT=9000 na API e 9000 no bloco upstream do Nginx).

5.4 Permissões de Volume de Storage no Host Linux

Ao montar pastas locais do host no container (/app/storage), se o usuário do container (connectos com UID 1000) não tiver permissão de escrita no diretório físico do host, uploads dispararão EStreamError: Access Denied. No host, execute sudo chown -R 1000:1000 ./storage para garantir a posse.

Glossário Técnico Geral da Trilogia

ACID: Propriedades de Atomicidade, Consistência, Isolamento e Durabilidade.

Circuit Breaker: Padrão de resiliência que interrompe temporariamente chamadas a serviços externos falhos para evitar saturação de recursos locais.

Cmem: Unit do Free Pascal que redireciona alocações de memória para a glibc (malloc/free) para evitar contenção em servidores multi-threaded.

Docker Multi-Stage: Técnica de criação de imagens que utiliza um contêiner para compilação e descarta o compilador, mantendo apenas o binário final.

Exponential Backoff: Cálculo de tempo de espera progressivo ($2^t$) em tentativas de repetição de chamadas de rede.

FPCUnit: Framework de testes unitários xUnit nativo do Free Pascal.

Graceful Shutdown: Encerramento controlado interceptando SIGTERM sem derrubar requisições HTTP ativas.

HeapTrc: Unidade diagnóstica de heap (-gh) para detectar vazamentos de memória no FPC.

LimitNOFILE: Limite de descritores de arquivos no systemd para suportar milhares de conexões de sockets TCP simultâneas.

OpenAPI 3.0: Padrão internacional para especificação e documentação de APIs RESTful em formato JSON.

Smartlinking: Otimização do compilador FPC (-XX) que elimina rotinas e units não utilizadas no binário final.

systemd: Sistema de gerenciamento e supervisão de daemons no Linux.
