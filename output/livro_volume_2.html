MÓDULO 09: ARQUITETURA LIMPA, MVC E INTERFACES NO LAZARUS

1. OBJETIVOS DE APRENDIZAGEM DO MÓDULO

Ao final deste módulo, você será capaz de:

  1. Aplicar os princípios da Clean Architecture (Arquitetura Limpa) e os fundamentos SOLID no ecossistema Object Pascal moderno com o Free Pascal Compiler (FPC) e o Lazarus.
  2. Projetar a separação estrita de responsabilidades entre as quatro camadas essenciais: Controladores HTTP (Horse), Serviços de Negócio (Services), Acesso a Dados (Repositories) e Objetos de Transferência (DTOs).
  3. Eliminar em definitivo o erro fatal de dependência circular entre units (Circular Unit Dependency), estruturando contratos formais em units isoladas de interfaces.
  4. Dominar o mecanismo de gerenciamento automático de memória por contagem de referências (Reference Counting) com IInterface e TInterfacedObject (_AddRef e _Release).
  5. Implementar Inversão de Controle (IoC) e Injeção de Dependências manual via construtores, viabilizando a substituição transparente de repositórios em testes e desacoplando as regras de negócio de drivers de banco.

2. FUNDAMENTAÇÃO CONCEITUAL E ARQUITETURAL

Historicamente, o desenvolvimento de software corporativo no ecossistema Pascal foi marcado pelo uso intensivo de componentes visuais do tipo RAD (Rapid Application Development). Era comum desenvolvedores arrastarem componentes de conexão de banco (TIBConnection, ZConnection) e queries (TSQLQuery, ZQuery) diretamente para dentro de um DataModule, acoplando no mesmo arquivo a interface gráfica, a lógica de validação de crédito e as instruções SQL de persistência.

Esse estilo arquitetural artesanal — frequentemente denominado "Smart UI" ou "código espaguete" — torna-se catastrófico ao construir APIs web modernas: - Impossibilidade de Testes Automatizados: Não é possível testar uma regra de negócio sem instanciar um banco de dados real e uma conexão de rede. - Acoplamento Extremo ao Framework Web: Se o controlador Horse manipula diretamente conexões com o banco, qualquer mudança no transporte (como migrar de HTTP para mensageria RabbitMQ ou gRPC) exige reescrever a aplicação inteira. - Risco de Corrupção Concorrente: Componentes visuais e DataModules tradicionais não foram projetados para serem compartilhados entre múltiplas threads concorrentes.

Para construir sistemas corporativos de classe mundial, adotamos os preceitos da Arquitetura Limpa formulados por Robert C. Martin (Uncle Bob), adaptados à semântica rigorosa do Free Pascal.

O Princípio de Inversão de Dependência (DIP)

O quinto princípio SOLID — Princípio da Inversão de Dependência (Dependency Inversion Principle) — estabelece duas regras invioláveis: 1. Módulos de alto nível não devem depender de módulos de baixo nível. Ambos devem depender de abstrações. 2. Abstrações não devem depender de detalhes. Detalhes devem depender de abstrações.

Na prática, isso significa que a nossa classe de serviço TClienteService (alto nível) nunca deve instanciar diretamente TClienteRepositoryFirebird (baixo nível). Em vez disso, a Service deve receber em seu construtor uma referência puramente contratual: a interface IClienteRepository.

Se amanhã decidirmos substituir o Firebird por PostgreSQL, ou se quisermos rodar um teste unitário com um repositório simulado em memória (Mock), o código da Service permanecerá rigorosamente intocado.

Eliminando Dependências Circulares no FPC

No compilador Free Pascal, cada arquivo .pas é uma unidade modular compilada separadamente. Se a unit A declara a unit B em sua seção interface, e a unit B declara a unit A em sua seção interface, o compilador FPC aborta imediatamente o processo com a falha:

Fatal: Circular dependency between A and B

A solução de engenharia definitiva para erradicar dependências circulares consiste em criar uma pasta dedicada src/Interfaces/ contendo units que declaram exclusivamente contratos de interface e DTOs puros. Nenhuma unit de interface jamais referencia uma unit de Service, Repository ou Controller. Todas as camadas superiores dependem da camada de Interfaces, mas as interfaces dependem de ninguém.

Gerenciamento de Memória com IInterface e TInterfacedObject

Uma das características mais poderosas do Free Pascal é o suporte nativo ao modelo de interfaces compatível com o padrão COM da Microsoft.

No FPC, qualquer interface declarada como descendente de IInterface (ou IUnknown) possui três métodos fundamentais:

function _AddRef: LongInt; stdcall;
function _Release: LongInt; stdcall;
function QueryInterface(constref iid: TGUID; out obj): HResult; stdcall;

Quando uma classe herda de TInterfacedObject, a biblioteca do FPC implementa automaticamente esses métodos através de um contador interno de referências (Reference Counting): 1. Atribuição: Toda vez que você atribui uma instância a uma variável de interface (ex: vRepo: IClienteRepository := TClienteRepository.Create;), o compilador insere nos bastidores uma chamada a _AddRef, incrementando o contador em 1. 2. Saída de Escopo: Quando o procedimento ou método onde a variável de interface foi declarada chega ao seu end; final, o compilador insere uma chamada a _Release, decrementando o contador em 1. 3. Autodestruição Determinística: No instante em que o contador de referências chega a zero, o próprio método _Release invoca Self.Destroy.

Boas Práticas FPC: > Ao trabalhar com instâncias gerenciadas por interfaces, **nunca invoque o método `.Free` manualmente**. Deixe que o mecanismo de contagem de referências do Free Pascal desaloque a memória automaticamente. Invocar `.Free` em um objeto que ainda possui referências ativas de interface causará violações de acesso (*SIGSEGV*) no momento em que a variável sair de escopo e o FPC tentar decrementar o contador de uma instância já destruída. --- ## 3. type
  { Servico de Dominio para Gestao de Clientes }
  TClienteService = class(TInterfacedObject, IClienteService)
  private
    FRepository: IClienteRepository;
  public
    constructor Create(ARepository: IClienteRepository);
    function ListarClientes(ATenantId: Int64; 
      APagina, ALimite: Integer; const ABusca: string): TList;
    function ObterCliente(ATenantId, AClienteId: Int64): TClienteDTO;
    function CadastrarCliente(ATenantId: Int64;

    procedure AtualizarCliente(ATenantId, AClienteId: Int64; 
      AInput: TClienteInputDTO);
    procedure RemoverCliente(ATenantId, AClienteId: Int64);
  end;

implementation

{ TClienteService }

constructor TClienteService.Create(ARepository: IClienteRepository);
begin
  inherited Create;
  { INJECAO DE DEPENDENCIA: A Service armazena a interface }
  FRepository := ARepository;
end;

function TClienteService.ListarClientes(ATenantId: Int64; 
  APagina, ALimite: Integer; const ABusca: string): TList;
begin
  if ATenantId <= 0 then
    raise EBusinessException.Create('Tenant invalido para listagem');

  if ALimite > 100 then
    ALimite := 100; { Protecao contra paginacao abusiva }

  Result := FRepository.Listar(ATenantId, APagina, ALimite, ABusca);
end;

function TClienteService.ObterCliente(ATenantId, 
  AClienteId: Int64): TClienteDTO;
begin
  if AClienteId <= 0 then
    raise EBusinessException.Create(
      'Identificador de cliente invalido');

  Result := FRepository.ObterPorId(ATenantId, AClienteId);
  if not Assigned(Result) then
    raise ENotFoundException.Create('Cliente nao localizado na base');
end;

function TClienteService.CadastrarCliente(ATenantId: Int64; 
  AInput: TClienteInputDTO): Int64;
var
  vExistente: TClienteDTO;
begin
  if not Assigned(AInput) then
    raise EBusinessException.Create('Dados do cliente ausentes');

  if Trim(AInput.NomeRazao) = '' then
    raise EBusinessException.Create('Razao Social e campo obrigatorio');

  if Length(Trim(AInput.CPFCNPJ)) < 11 then
    raise EBusinessException.Create('Documento CPF/CNPJ invalido');

  { Checagem de unicidade atraves do repositorio }
  vExistente := FRepository.ObterPorDocumento(
    ATenantId, AInput.CPFCNPJ);
  if Assigned(vExistente) then
  begin
    vExistente.Free;
    raise EConflictException.Create(
      'Ja existe um cliente cadastrado com este CPF/CNPJ');
  end;

  Result := FRepository.Inserir(ATenantId, AInput);
end;

procedure TClienteService.AtualizarCliente(
  ATenantId, AClienteId: Int64; AInput: TClienteInputDTO);
var
  vAtual: TClienteDTO;
begin
  vAtual := ObterCliente(ATenantId, AClienteId);
  vAtual.Free;

  FRepository.Atualizar(ATenantId, AClienteId, AInput);
end;

procedure TClienteService.RemoverCliente(ATenantId, AClienteId: Int64);
var
  vAtual: TClienteDTO;
begin
  vAtual := ObterCliente(ATenantId, AClienteId);
  vAtual.Free;

  FRepository.Excluir(ATenantId, AClienteId);
end;

end.

unit Controllers.Clientes;

{$mode objfpc}{$H+}

interface

uses
  SysUtils,
  Classes,
  fpjson,
  Horse,
  Interfaces.Cliente,
  Services.Cliente,
  Repositories.Cliente,
  DTOs.Cliente,
  Core.Exceptions;

type
  TControllersClientes = class
  private
    class function CriarService: IClienteService; static;
    class procedure Listar(Req: THorseRequest; Res: THorseResponse; 
      Next: TNextProc);
    class procedure ObterPorId(Req: THorseRequest; Res: THorseResponse; 
      Next: TNextProc);
    class procedure Criar(Req: THorseRequest; Res: THorseResponse; 
      Next: TNextProc);
    class procedure Excluir(Req: THorseRequest; Res: THorseResponse; 
      Next: TNextProc);
  public
    class procedure Registry;
  end;

implementation

{ TControllersClientes }

class function TControllersClientes.CriarService: IClienteService;
begin
  { Factory leve: instancia o repositorio e injeta na Service }
  Result := TClienteService.Create(TClienteRepository.Create);
end;

class procedure TControllersClientes.Listar(Req: THorseRequest; 
  Res: THorseResponse; Next: TNextProc);
var
  vService: IClienteService;
  vTenantId: Int64;
  vLista: TList;
  vEnvelope: TJSONObject;
  vItens: TJSONArray;
  i: Integer;
begin
  vTenantId := StrToInt64Def(
    Req.Headers.Field('X-Tenant-ID').AsString, 1);

  vService := CriarService;
  vLista := vService.ListarClientes(vTenantId, 1, 10, '');
  try
    vEnvelope := TJSONObject.Create;
    vItens := TJSONArray.Create;

    for i := 0 to vLista.Count - 1 do
      vItens.Add(TClienteDTO(vLista[i]).ToJSONObject);

    vEnvelope.Add('total', vLista.Count);
    vEnvelope.Add('dados', vItens);

    Res.Send(vEnvelope)
       .Status(THTTPStatus.OK);
  finally
    for i := 0 to vLista.Count - 1 do
      TClienteDTO(vLista[i]).Free;
    vLista.Free;
  end;
end;

class procedure TControllersClientes.ObterPorId(Req: THorseRequest; 
  Res: THorseResponse; Next: TNextProc);
var
  vService: IClienteService;
  vTenantId, vClienteId: Int64;
  vDTO: TClienteDTO;
begin
  vTenantId := 1;
  vClienteId := StrToInt64Def(Req.Params.Field('id').AsString, 0);

  vService := CriarService;
  vDTO := vService.ObterCliente(vTenantId, vClienteId);
  try
    Res.Send(vDTO.ToJSONObject)
       .Status(THTTPStatus.OK);
  finally
    vDTO.Free;
  end;
end;

class procedure TControllersClientes.Criar(Req: THorseRequest; 
  Res: THorseResponse; Next: TNextProc);
var
  vService: IClienteService;
  vInputJSON: TJSONObject;
  vInputDTO: TClienteInputDTO;
  vNovoId: Int64;
  vResposta: TJSONObject;
begin
  vInputJSON := Req.Body<TJSONObject>();
  if not Assigned(vInputJSON) then
    raise EAppException.Create('Payload JSON ausente', 400);

  vInputDTO := TClienteInputDTO.FromJSONObject(vInputJSON);
  try
    vService := CriarService;
    vNovoId := vService.CadastrarCliente(1, vInputDTO);

    vResposta := TJSONObject.Create;
    vResposta.Add('id', vNovoId);
    vResposta.Add('mensagem', 'Cadastrado via Clean Architecture');

    Res.RawWebResponse.SetCustomHeader('Location', 
      '/api/v1/clientes/' + IntToStr(vNovoId));

    Res.Send(vResposta)
       .Status(THTTPStatus.Created);
  finally
    vInputDTO.Free;
  end;
end;

class procedure TControllersClientes.Excluir(Req: THorseRequest; 
  Res: THorseResponse; Next: TNextProc);
var
  vService: IClienteService;
  vClienteId: Int64;
begin
  vClienteId := StrToInt64Def(Req.Params.Field('id').AsString, 0);
  vService := CriarService;
  vService.RemoverCliente(1, vClienteId);

ARMADILHAS COMUNS E TROUBLESHOOTING NO FPC/LAZARUS --- ### Armadilha 1: Misturar Ponteiros de Objeto Puro com Interfaces **Sintoma:** Violação de acesso (*SIGSEGV*) aleatória ao sair de um procedimento onde uma interface e um objeto concreto foram utilizados simultaneamente. **Causa Raiz:** O desenvolvedor instancia a classe em uma variável concreta e atribui à interface, invocando `.Free` na variável concreta: 
{ EQUIVOCO GRAVE: Dangling Pointer }
var
  vObj: TClienteRepository;
  vIntf: IClienteRepository;
begin
  vObj := TClienteRepository.Create;
  vIntf := vObj; { Contador de ref = 1 }
  vObj.Free;     { Destroi o objeto manualmente! }
  { Ao sair, vIntf chama _Release e acessa memoria morta }
end;
**Solução:** Ao utilizar interfaces, atribua **diretamente** o resultado de `.Create` à variável de interface, sem variáveis intermediárias de classe: 
var
  vIntf: IClienteRepository;
begin
  vIntf := TClienteRepository.Create; { 100% seguro }
end;
--- ### Armadilha 2: Esquecer de Herdar de TInterfacedObject **Sintoma:** O compilador acusa erro de métodos abstratos não implementados: 
Error: No matching implementation for interface method "_AddRef" found
**Causa Raiz:** A classe foi declarada como `class(TObject, IMinhaInterface)`. O `TObject` básico não implementa `_AddRef`, `_Release` e `QueryInterface`. **Solução:** Todas as classes que implementam interfaces no FPC devem herdar de `TInterfacedObject`: 
type
  TMeuServico = class(TInterfacedObject, IMeuServico)
--- ### Armadilha 3: Dependência Circular por Falta de Camada de Contratos **Sintoma:** O arquivo `Services.Cliente.pas` tenta referenciar `Controllers.Clientes.pas` e o compilador aborta com `Fatal: Circular dependency`. **Causa Raiz:** Comunicação bidirecional desordenada entre camadas superiores e inferiores. **Solução:** A camada de controladores pode enxergar a camada de serviços, mas a camada de serviços **nunca** deve enxergar a camada de controladores. ### O Conjunto de Caracteres UTF8 e a Eliminação da Falha de Transliteração A especificação do protocolo HTTP e do formato JSON (RFC 8259) determina que o tráfego de dados na web moderna deve ser estritamente codificado em **UTF-8**. Nas versões antigas do Firebird (1.5 e 2.x), era comum desenvolvedores criarem bancos com conjuntos legados de caracteres, como `WIN1252` ou `ISO8859_1`. Quando uma API em Horse recebia caracteres acentuados (como *"Manutenção e Diagnóstico"*), caracteres com emojis ou símbolos monetários (`R$`, `€`), e tentava gravá-los no banco sem correspondência direta de byte, o driver de banco lançava a exceção clássica: 
GDS Code: 335544569 -
Cannot transliterate character between character sets
No Firebird 5.0, a regra de ouro para qualquer API RESTful corporativa é unificar toda a cadeia em UTF-8: 1. **No Banco Físico:** Criação do banco com `DEFAULT CHARACTER SET UTF8`. 2. **Nas Conexões de Rede:** Configuração obrigatória do parâmetro `lc_ctype=UTF8` na string de conexão do cliente. 3. **Na Camada Pascal:** Compilação do código com `{$H+}` (AnsiString/UTF8 dinâmica nativa). Com esses três pilares alinhados, a transliteração torna-se puramente transparente: zero perdas de acentuação e zero erros de charset. --- ### Colunas IDENTITY: Modernidade sem Triggers Artesanais No Firebird clássico, a criação de chaves primárias autoincrementais exigia dois artefatos manuais por tabela: 1. Uma Sequence/Generator dedicada: `CREATE SEQUENCE gen_clientes_id;` 2. Uma Trigger *Before Insert* obrigatória: ```sql /* MODELO LEGADO E OBSOLETO - NÃO UTILIZE NO FIREBIRD 5 */ CREATE TRIGGER trg_clientes_bi FOR clientes BEFORE INSERT AS BEGIN IF (NEW.id IS NULL) THEN NEW.id = NEXT VALUE FOR gen_clientes_id; END ``` Essa abordagem antiga carregava deficiências graves: poluição do catálogo de metadados, lentidão em operações de inserção em massa (*bulk insert*) e necessidade de transações adicionais para capturar o ID gerado via `GEN_ID(gen_clientes_id, 0)`. A partir das versões modernas e consolidado com maestria no **Firebird 5.0**, adotamos a sintaxe nativa padrão **ANSI SQL:2008**: 
CREATE TABLE clientes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ...
);
Vantagens da coluna `IDENTITY`: - **Semântica `BY DEFAULT`:** Se o cliente não informar o ID no comando `INSERT`, o motor do Firebird gera automaticamente o próximo valor da sequência interna. Se um processo de replicação ou migração de dados informar um ID explicitamente, o banco respeita o valor informado. - **Tipagem em `BIGINT` (64 bits):** Chaves primárias devem utilizar inteiros de 64 bits (`Int64` no Pascal). O limite de um inteiro de 32 bits (`INTEGER` - 2,14 bilhões) é facilmente superado em tabelas volumosas de ordens de serviço, itens ou logs de auditoria em ambientes SaaS. - **Desempenho Extremo:** A geração do valor ocorre diretamente no núcleo C++ do motor do banco, sem o overhead de disparar o interpretador PSQL para executar triggers. ### A Cláusula RETURNING: Atomicidade em uma Única Viagem de Rede Quando uma API executa um comando `POST` para criar um cliente, o protocolo HTTP 201 Created exige que a resposta informe o identificador gerado e emita o cabeçalho `Location: /api/v1/clientes/:id`. No passado, os desenvolvedores executavam o `INSERT`, fechavam a query e disparavam uma segunda consulta (`SELECT FIRST 1 id FROM ... ORDER BY id DESC`) para descobrir qual ID havia sido atribuído. Essa prática gerava condições de corrida (*race conditions*) perigosas em ambientes concorrentes e dobrava a latência de rede. No Firebird 5.0, a cláusula **`RETURNING`** resolve esse problema atomicamente: 
INSERT INTO clientes (tenant_id, nome_razao, cpf_cnpj)
VALUES (1, 'Oficina Mecanica Central', '11222333000199')
RETURNING id, created_at;
O comando executa a inserção e devolve imediatamente o ID gerado pelo `IDENTITY` e o timestamp gerado pelo servidor em um único pacote TCP, garantindo velocidade máxima e consistência transacional absoluta. --- ### Modelagem Física Multi-Tenant: A Estratégia de Banco Compartilhado Em plataformas de software como serviço (SaaS), existem três modelos clássicos de isolamento de dados: 1. *Banco por Inquilino (Database per Tenant):* Um arquivo `.fdb` físico separado para cada cliente. Oferece isolamento total, mas inviabiliza a manutenção quando a base atinge centenas de inquilinos (complexidade extrema de migrações DDL e saturação de pools). 2. *Schema por Inquilino (Schema per Tenant):* Suportado por bancos como PostgreSQL, mas inexistente no Firebird. 3. *Banco Compartilhado com Coluna Discriminadora (Shared Database, Shared Schema):* Todas as empresas compartilham o mesmo banco de dados físico e as mesmas tabelas, sendo rigorosamente isoladas por uma coluna mandatória: **`tenant_id`**. A abordagem de **Banco Compartilhado** é a mais eficiente, econômica e escalável para a nossa **ConnectOSApi**.

### Por que a Biblioteca fbclient Não É Reentrante na Mesma Conexão? A biblioteca nativa do Firebird (`fbclient.dll` / `libfbclient.so`) utiliza ponteiros de baixo nível da API em linguagem C: - **`isc_db_handle`:** Identificador numérico da conexão física com o servidor. - **`isc_tr_handle`:** Identificador da transação ativa associada àquele canal. Quando uma query é executada, o cliente envia um pacote pelo socket TCP na porta 3050 e aguarda os pacotes de resposta do servidor Firebird. Se duas threads utilizarem o mesmo `isc_db_handle` simultaneamente: 1. Uma thread envia uma instrução `INSERT` enquanto a outra envia um `SELECT`. 2. As respostas de rede retornadas pelo servidor Firebird se misturam no buffer de recepção da biblioteca. 3. O driver C do Firebird tenta atribuir linhas de consulta para a transação que esperava apenas a confirmação da inserção. 4. O processo é sumariamente abortado pelo sistema operacional com violação de acesso (*SIGSEGV*), ou o banco emite o erro: ```text Dynamic SQL Error: SQL error code = -902. Network error. ``` ### Abrir e Fechar em Cada Requisição? O Custo Proibitivo de Latência Percebendo que conexões globais geram corrupção, alguns desenvolvedores adotam a solução ingênua oposta: instanciar uma nova conexão no início de cada rota (`TIBConnection.Create`) e destruí-la ao final (`Connection.Free`). Embora thread-safe, essa prática destrói o desempenho da API corporativa: - **Handshake TCP:** Abertura e fechamento de conexões na porta 3050 em cada clique. - **Aperto de Mão Criptográfico:** Autenticação de credenciais SRP (*Secure Remote Password*) do usuário `SYSDBA` exigindo cálculo de chaves simétricas na CPU. - **Alocação de Recursos no Servidor:** O Firebird precisa alocar páginas de memória dedicadas e descritores no processo SuperServer a cada nova conexão física. Medições de laboratório revelam que estabelecer uma conexão física com o Firebird consome entre **15 ms e 45 ms** de latência de rede. Se a sua consulta SQL leva apenas 0,5 ms para ser executada, você estará desperdiçando 98% do tempo da requisição apenas abrindo e fechando o soquete!

### O Padrão RAII com Interfaces Gerenciadas (IConnectionWrapper) Como garantir que uma conexão emprestada do pool seja **obrigatoriamente devolvida**, mesmo se a rota lançar uma exceção de validação, erro de sintaxe SQL ou perda de conexão? A técnica mais robusta no Free Pascal reside no padrão **RAII (Resource Acquisition Is Initialization)** utilizando interfaces: 1. O controlador solicita uma conexão ao pool recebendo a interface **`IConnectionWrapper`**. 2. A interface encapsula a referência física da conexão (`TIBConnection`) e de sua transação associada. 3. Quando o procedimento da rota atinge o seu `end;` final — seja pelo fluxo feliz ou por desenrolamento da pilha de exceções (*exception unwinding*) —, o compilador FPC invoca automaticamente o método `_Release` da interface. 4. O destrutor do wrapper intercepta a liberação e devolve a conexão física de volta à fila de conexões disponíveis do pool, garantindo **zero vazamentos de conexões (*zero connection leaks*)**. --- ## 3. constructor TPooledConnection.Create(const AHost, ABanco, AUser, 
  APass: string; APorta: Integer);

  inherited Create;

  CriadaEm := GetTickCount64;
  UltimoUsoEm := CriadaEm;

  { Configuracao nativa da conexao Firebird com SQLdb }

begin
  try
    if Transaction.Active then
      Transaction.Rollback;
  except
  end;

  try
    if Connection.Connected then
      Connection.Close;
  except
  end;

  Transaction.Free;
  Connection.Free;
  inherited Destroy;
end;

      Result := not vQry.IsEmpty;
      vQry.Close;
    finally
      vQry.Free;
    end;
  except
    Result := False;
  end;
end;

  end;

function TFirebirdConnectionPool.Acquire: IConnectionWrapper;
var
  vInicioMS: QWord;
  i: Integer;
  vItem: TPooledConnection;
begin
  vInicioMS := GetTickCount64;

  while True do
  begin
    FSection.Enter;
    try
      { 1. Procura conexao ociosa disponivel }
      for i := 0 to FConexoes.Count - 1 do
      begin
        vItem := TPooledConnection(FConexoes[i]);
        if not vItem.EmUso then
        begin
          { Validacao rapida de saude da conexao }
          if vItem.EstaAtiva then
          begin
            vItem.EmUso := True;
            vItem.UltimoUsoEm := GetTickCount64;
            Exit(TConnectionWrapper.Create(vItem));
          end
          else
          begin
            { Conexao rompida: descarta e recria }
            vItem.Free;
            vItem := CriarConexaoFisica;
            vItem.EmUso := True;
            FConexoes[i] := vItem;
            Exit(TConnectionWrapper.Create(vItem));
          end;
        end;
      end;

      { 2. Se nao ha ociosa mas nao atingiu o maximo, expande o pool }
      if FConexoes.Count < FMaxPoolSize then
      begin
        vItem := CriarConexaoFisica;
        vItem.EmUso := True;
        FConexoes.Add(vItem);
        Exit(TConnectionWrapper.Create(vItem));
      end;
    finally
      FSection.Leave;
    end;

    { 3. Todas em uso: aguarda liberacao ate o timeout }
    if (GetTickCount64 - vInicioMS) >= QWord(FAcquireTimeoutMS) then
      raise EAppException.Create(
        'Timeout: Pool de conexoes Firebird esgotado', 503);

    Sleep(10); { Espera cooperativa de 10 ms para despressurizar CPU }
  end;
end;

procedure TFirebirdConnectionPool.ReleaseConnection(
  APooled: TPooledConnection);
begin
  if not Assigned(APooled) then
    Exit;

  FSection.Enter;
  try
    APooled.EmUso := False;
    APooled.UltimoUsoEm := GetTickCount64;
  finally
    FSection.Leave;
  end;
end;

function TFirebirdConnectionPool.TotalConexoes: Integer;
begin
  FSection.Enter;
  try
    Result := FConexoes.Count;
  finally
    FSection.Leave;
  end;
end;

function TFirebirdConnectionPool.ConexoesEmUso: Integer;
var
  i: Integer;
begin
  Result := 0;
  FSection.Enter;
  try
    for i := 0 to FConexoes.Count - 1 do
      if TPooledConnection(FConexoes[i]).EmUso then
        Inc(Result);
  finally
    FSection.Leave;
  end;
end;

Fundamentação Conceitual e Arquitetural ### 2.1 O Ciclo Transacional ACID no Firebird 5.0 Em sistemas web concorrentes, a integridade dos dados depende da disciplina com que as transações são tratadas. No Firebird, cada comando SQL de leitura ou escrita deve obrigatoriamente residir dentro de um contexto transacional ativo (`TSQLTransaction`). Para o nosso cenário de APIs REST, adotamos a configuração de transação com isolamento `READ COMMITTED` e resolução de conflito `NOWAIT`: 
+--------------------------------------------------------------------+
| PARAMETROS DO TSQLTransaction (READ COMMITTED + NOWAIT)            |
|                                                                    |
| isc_tpb_read_committed : Enxerga dados commitados por outros       |
| isc_tpb_rec_version    : Le versao mais recente sem lock de leitura|
| isc_tpb_nowait         : Retorna erro de lock de imediato (sem hang)|
+--------------------------------------------------------------------+
Essa combinação garante que uma requisição HTTP nunca fique congelada esperando um lock de linha indefinidamente. Se outra thread estiver alterando o mesmo registro de estoque ou fatura, a transação recebe um erro imediato, que é capturado pelo nosso middleware de exceções e convertido em `409 Conflict` ou `422 Unprocessable Entity`.
Atenção Thread-Safety: > No modelo multi-threaded do `fphttpserver`, nunca reutilize uma instância > de `TSQLTransaction` entre threads. Cada transação pertence exclusivamente > à sua respectiva conexão física adquirida do Pool. Transações compartilhadas > causam corrupção de ponteiros internos da `fbclient` e abortam o processo. ### 2.2 O Perigo Fatal do `CommitRetaining` em APIs REST Desenvolvedores Delphi/Lazarus migrando do desenvolvimento desktop clássico para o ambiente web frequentemente cometem o erro grave de invocar `Transaction.CommitRetaining` em vez de `Transaction.Commit`. No Firebird, `CommitRetaining` persiste as alterações no disco, mas **mantém o contexto da transação aberto**, preservando a mesma Transaction ID (TID). Em uma API de alta taxa de requisições, isso impede que a OAT (*Oldest Active Transaction*) avance. Como consequência: 1. O processo de Garbage Collection do Firebird é paralisado. 2. As versões antigas dos registros acumuladas em disco não são expurgadas. 3. O arquivo de banco de dados (`.fdb`) incha rapidamente e a performance geral do servidor colapsa em poucas horas.
Boas Práticas FPC: > Em servidores de API REST, **jamais utilize `CommitRetaining`**. Toda > transação deve ter um ciclo de vida curto: `StartTransaction` -> Execução > de SQLs -> `Commit` (ou `Rollback` na cláusula `except`). ### 2.3 O Padrão Unit of Work O padrão Unit of Work mantém uma lista de objetos afetados por uma transação de negócios e coordena a gravação dessas alterações e a resolução de problemas de concorrência. Na nossa implementação em Lazarus, o Unit of Work encapsula o `IConnectionWrapper`, garantindo que os repositórios de `OrdemServico` e `ItemOrdemServico` operem exatamente sobre a mesma conexão e transação física: 
+--------------------------------------------------------------------+
|                    Unit of Work (IUnitOfWork)                      |
|  - Gerencia IConnectionWrapper obtido atomicamente do Pool         |
|  - Inicia transacao explicita (StartTransaction)                   |
|  - Repassa conexao/transacao para Repositories dependentes         |
|  - Efetua Commit ou Rollback garantido via try..finally            |
+--------------------------------------------------------------------+

         |                                                   |
         v                                                   v
+-------------------------------+   +-------------------------------+
|   IOrdemServicoRepository     |   |     IItemOrdemServicoRepo     |
|   Persiste cabecalho da OS    |   |   Persiste itens e servicos   |
|   (INSERT INTO ordens_servico)|   |   (INSERT INTO itens_os)      |
+-------------------------------+   +-------------------------------+

  vQry: TSQLQuery;

  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;
    vQry.SQL.Text := 
      'INSERT INTO ordens_servico (' +

      '  observacoes, valor_total, criado_em' +

      '  :obs, :total, CURRENT_TIMESTAMP' +

function TOrdemServicoService.CalcularTotal(
  ADTO: TOrdemServicoInputDTO): Double;
var
  i: Integer;
begin
  Result := 0.0;
  for i := 0 to ADTO.TotalItens - 1 do
    Result := Result + (ADTO.Itens[i].Quantidade * 
      ADTO.Itens[i].ValorUnitario);
end;

procedure TOrdemServicoService.ValidarTransicaoStatus(
  const AStatusAtual, ANovoStatus: string);
begin
  if AStatusAtual = ANovoStatus then Exit;

  if (AStatusAtual = 'CONCLUIDA') or (AStatusAtual = 'CANCELADA') then
    raise EBusinessException.Create(
      'Ordem de Servico finalizada nao permite alteracao de status');

  if (AStatusAtual = 'ABERTA') and (ANovoStatus <> 'EM_EXECUCAO') and 
     (ANovoStatus <> 'CANCELADA') then
    raise EBusinessException.Create(
      'OS Aberta so transiciona para EM_EXECUCAO ou CANCELADA');

  if (AStatusAtual = 'EM_EXECUCAO') and 
     (ANovoStatus <> 'CONCLUIDA') and (ANovoStatus <> 'CANCELADA') then
    raise EBusinessException.Create(
      'OS Em Execucao so transiciona para CONCLUIDA ou CANCELADA');
end;

function TOrdemServicoService.CriarOS(const ATenantId: Int64; 
  ADTO: TOrdemServicoInputDTO): TOrdemServicoOutputDTO;
var
  vUoW: IUnitOfWork;
  vRepo: IOrdemServicoRepository;
  vTotal: Double;
  vNovoId: Int64;
  i: Integer;
begin
  ADTO.Validar;
  vTotal := CalcularTotal(ADTO);

  vUoW := TUnitOfWork.Create;
  vRepo := TOrdemServicoRepository.Create(vUoW);

  vUoW.BeginTransaction;
  try
    vNovoId := vRepo.InserirCabecalho(ATenantId, ADTO, vTotal);
    for i := 0 to ADTO.TotalItens - 1 do
      vRepo.InserirItem(ATenantId, vNovoId, ADTO.Itens[i]);

    vUoW.Commit;
  except
    vUoW.Rollback;
    raise;
  end;

  Result := vRepo.ObterPorId(ATenantId, vNovoId);
end;

function TOrdemServicoService.BuscarPorId(const ATenantId, 
  AOSId: Int64): TOrdemServicoOutputDTO;
var
  vUoW: IUnitOfWork;
  vRepo: IOrdemServicoRepository;
begin
  vUoW := TUnitOfWork.Create;
  vRepo := TOrdemServicoRepository.Create(vUoW);
  Result := vRepo.ObterPorId(ATenantId, AOSId);
  if not Assigned(Result) then
    raise ENotFoundException.Create(
      Format('Ordem de Servico %d nao encontrada', [AOSId]));
end;

procedure TOrdemServicoService.MudarStatus(const ATenantId, 
  AOSId: Int64; const ANovoStatus: string);
var
  vUoW: IUnitOfWork;
  vRepo: IOrdemServicoRepository;
  vOS: TOrdemServicoOutputDTO;
  vStatusUpper: string;
begin
  vStatusUpper := UpperCase(Trim(ANovoStatus));
  vUoW := TUnitOfWork.Create;
  vRepo := TOrdemServicoRepository.Create(vUoW);

  vOS := vRepo.ObterPorId(ATenantId, AOSId);
  if not Assigned(vOS) then
    raise ENotFoundException.Create(
      Format('Ordem de Servico %d nao encontrada', [AOSId]));
  try
    ValidarTransicaoStatus(vOS.Status, vStatusUpper);
    vUoW.BeginTransaction;
    try
      vRepo.AtualizarStatus(ATenantId, AOSId, vStatusUpper);
      vUoW.Commit;
    except
      vUoW.Rollback;
      raise;
    end;
  finally
    vOS.Free;
  end;
end;

procedure TOrdemServicoService.CancelarOS(const ATenantId, 
  AOSId: Int64);
begin
  MudarStatus(ATenantId, AOSId, 'CANCELADA');
end;

end.

Armadilhas Comuns e Troubleshooting no FPC/Lazarus ### 5.1 O Erro Fatal de Abrir Query com Transação Inativa No `SQLdb`, ao invocar `vQry.Open` ou `vQry.ExecSQL` sem que `Transaction.StartTransaction` tenha sido chamado previamente, o FPC inicia a transação implicitamente. Contudo, se a transação for implícita, muitos programadores esquecem de chamar `Commit`, deixando cursores abertos na `fbclient`. **Regra de ouro:** Sempre controle a abertura explicitamente através do `IUnitOfWork.BeginTransaction`. ### 5.2 Não Limpar Cursores de `TSQLQuery` Antes do `Commit` Se um `TSQLQuery` permanecer aberto no momento em que `Transaction.Commit` for executado, a `fbclient` fecha o cursor abruptamente ou pode disparar a exceção `Transaction is active`. **Solução:** Garanta que todas as instâncias de `TSQLQuery` criadas na rotina sejam destruídas (`vQry.Free`) antes do fechamento formal da transação no Unit of Work. ### 5.3 Conflito de Concorrência com Deadlock Se duas requisições concorrentes tentarem atualizar simultaneamente a mesma linha com a transação configurada em `NOWAIT`, o Firebird 5.0 lança imediatamente o erro de código `isc_deadlock` ou `isc_lock_conflict`. Para mitigar isso: 1. Mantenha as transações de escrita o mais curtas possível. 2. Execute todos os cálculos e validações em memória antes de disparar o `BeginTransaction`. 3. Ordene a inserção de itens de forma determinística (por exemplo, ordenando por `produto_id` ou índice crescente) para evitar bloqueios cruzados. --- ## 6. # Módulo 13: Paginação de Alta Performance, Filtros Dinâmicos e Metadados Construir endpoints de listagem que escalam graciosamente com o crescimento da base de dados é um dos desafios mais críticos no desenvolvimento de APIs REST corporativas. Em sistemas de faturamento e ordens de serviço, tabelas facilmente acumulam milhões de registros. Uma consulta ingênua que retorne um volume irrestrito de dados pode saturar a memória RAM do servidor Lazarus, esgotar a banda da rede e congelar o banco de dados. Neste módulo, exploraremos a sintaxe moderna de paginação introduzida no padrão SQL:2008 e refinada no **Firebird 5.0** (`OFFSET ... FETCH NEXT ... ROWS ONLY`), comparando-a com os tradicionais comandos `FIRST/SKIP`. Construiremos um mecanismo robusto de filtros dinâmicos totalmente blindado contra SQL Injection, suporte a ordenação controlada via *whitelist* de colunas e um envelope JSON padronizado com metadados completos de navegação. --- ## 1. Fundamentação Conceitual e Arquitetural ### 2.1 Evolução da Paginação no Firebird: De `FIRST/SKIP` a `OFFSET/FETCH` Historicamente, o Firebird utilizava as diretivas proprietárias `FIRST m SKIP n` posicionadas logo após o comando `SELECT`: 
/* Sintaxe Legada (Firebird 2.x/3.x) */
SELECT FIRST 10 SKIP 20 o.id, o.valor_total
FROM ordens_servico o
ORDER BY o.id DESC;
A partir do Firebird 3.0 e consolidado como padrão de alta performance no **Firebird 5.0**, a engine adotou o padrão ANSI SQL:2008: 
/* Sintaxe Padrao ANSI (Firebird 5.0) */
SELECT o.id, o.valor_total
FROM ordens_servico o
ORDER BY o.id DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;
A nova sintaxe traz vantagens conceituais expressivas: - **Compatibilidade Padronizada:** A consulta torna-se compatível com outros grandes SGBDs (PostgreSQL, Oracle, SQL Server). - **Semântica Posicional Clara:** As cláusulas de paginação residem no final da consulta, facilitando a montagem dinâmica em código Pascal sem necessidade de manipular o cabeçalho do `SELECT`. - **Otimização no Firebird 5.0:** O otimizador de consultas avalia os índices e evita a leitura física de linhas descartadas pelo `OFFSET` quando há um índice ordenado compatível com o `ORDER BY`. 
+--------------------------------------------------------------------+
|  FLUXO DE EXECUCAO DO OFFSET / FETCH NO FIREBIRD 5.0              |
|                                                                    |
|  1. Filtra por tenant_id e condicoes (Index Range Scan)            |
|  2. Percorre indice ordenado saltando n linhas (OFFSET n ROWS)     |
|  3. Recupera fisicamente apenas m registros (FETCH NEXT m ONLY)    |
|  4. Retorna cursor estrito sem alocar tabela inteira em memoria    |

### 2.2 O Perigo Crítico de SQL Injection em Filtros Dinâmicos Um erro frequente em aplicações comerciais é concatenar strings diretamente na cláusula `WHERE` para atender múltiplos filtros opcionais: 
{ CODIGO INSEGURO - NUNCA UTILIZE EM PRODUCAO }
vSQL := 'SELECT * FROM ordens_servico WHERE tenant_id = ' + vTenant;
if vStatus <> '' then
  vSQL := vSQL + ' AND status = ''' + vStatus + ''''; 
  { VULNERABILIDADE ACIMA! }
Se o parâmetro `vStatus` contiver a carga `' OR '1'='1`, a cláusula é corrompida e dados de outros tenants vazam na resposta.
Nota de Arquitetura: > **Parâmetros SQL são invioláveis.** Qualquer filtro dinâmico deve gerar > placeholders nomeados (ex: `:status`, `:cliente_id`) e injetar os > respectivos valores exclusivamente através da propriedade `ParamByName` > do `TSQLQuery`. ### 3.2 O Construtor Seguro de Consultas SQL (`Core.SQLBuilder.pas`) Para garantir que toda cláusula `WHERE` e seus valores sejam completamente parametrizados, construímos um componente utilitário `TSQLFilterBuilder`: 
unit Core.SQLBuilder;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, sqldb;

type
  { Representa um parametro tipado a ser injetado na query }
  TParamType = (ptString, ptInt64, ptFloat, ptDateTime);

  TFilterParam = record
    Nome: string;
    Tipo: TParamType;
    ValorString: string;
    ValorInt64: Int64;
    ValorFloat: Double;
    ValorDateTime: TDateTime;
  end;

  { Construtor dinâmico de clausulas WHERE e ORDER BY seguras }
  TSQLFilterBuilder = class
  private
    FClausulas: TStringList;
    FParams: array of TFilterParam;
    procedure AdicionarParametro(const ANome: string; 
      ATipo: TParamType; const AValStr: string; AValInt: Int64; 
      AValFloat: Double; AValDate: TDateTime);
  public
    constructor Create;
    destructor Destroy; override;
    procedure AdicionarCondicao(const ACondicao: string);
    procedure AdicionarFiltroTexto(const ACampo, ANomeParam, 
      AValor: string);
    procedure AdicionarFiltroInt64(const ACampo, ANomeParam: string; 
      const AValor: Int64);
    procedure AdicionarFiltroFloat(const ACampo, ANomeParam: string; 
      const AValor: Double);
    function MontarClausulaWhere: string;
    procedure AplicarParametros(AQry: TSQLQuery);
  end;

implementation

constructor TSQLFilterBuilder.Create;
begin
  inherited Create;
  FClausulas := TStringList.Create;
end;

destructor TSQLFilterBuilder.Destroy;
begin
  FClausulas.Free;
  inherited Destroy;
end;

procedure TSQLFilterBuilder.AdicionarParametro(const ANome: string; 
  ATipo: TParamType; const AValStr: string; AValInt: Int64; 
  AValFloat: Double; AValDate: TDateTime);
var
  vIdx: Integer;
begin
  vIdx := Length(FParams);
  SetLength(FParams, vIdx + 1);
  FParams[vIdx].Nome := ANome;
  FParams[vIdx].Tipo := ATipo;
  FParams[vIdx].ValorString := AValStr;
  FParams[vIdx].ValorInt64 := AValInt;
  FParams[vIdx].ValorFloat := AValFloat;
  FParams[vIdx].ValorDateTime := AValDate;
end;

procedure TSQLFilterBuilder.AdicionarCondicao(const ACondicao: string);
begin
  FClausulas.Add(ACondicao);
end;

procedure TSQLFilterBuilder.AdicionarFiltroTexto(const ACampo, 
  ANomeParam, AValor: string);
begin
  if Trim(AValor) <> '' then
  begin
    FClausulas.Add(Format('%s = :%s', [ACampo, ANomeParam]));
    AdicionarParametro(ANomeParam, ptString, Trim(AValor), 0, 0.0, 0);
  end;
end;

procedure TSQLFilterBuilder.AdicionarFiltroInt64(const ACampo, 
  ANomeParam: string; const AValor: Int64);
begin
  if AValor > 0 then
  begin
    FClausulas.Add(Format('%s = :%s', [ACampo, ANomeParam]));
    AdicionarParametro(ANomeParam, ptInt64, '', AValor, 0.0, 0);
  end;
end;

procedure TSQLFilterBuilder.AdicionarFiltroFloat(const ACampo, 
  ANomeParam: string; const AValor: Double);
begin
  if AValor > 0 then
  begin
    FClausulas.Add(Format('%s = :%s', [ACampo, ANomeParam]));
    AdicionarParametro(ANomeParam, ptFloat, '', 0, AValor, 0);
  end;
end;

function TSQLFilterBuilder.MontarClausulaWhere: string;
var
  i: Integer;
begin
  if FClausulas.Count = 0 then
    Exit('');

  Result := ' WHERE ' + FClausulas[0];
  for i := 1 to FClausulas.Count - 1 do
    Result := Result + ' AND ' + FClausulas[i];
end;

procedure TSQLFilterBuilder.AplicarParametros(AQry: TSQLQuery);
var
  i: Integer;
begin
  for i := 0 to High(FParams) do
  begin
    case FParams[i].Tipo of
      ptString:
        AQry.ParamByName(FParams[i].Nome).AsString := 
          FParams[i].ValorString;
      ptInt64:
        AQry.ParamByName(FParams[i].Nome).AsLargeInt := 
          FParams[i].ValorInt64;
      ptFloat:
        AQry.ParamByName(FParams[i].Nome).AsFloat := 
          FParams[i].ValorFloat;
      ptDateTime:
        AQry.ParamByName(FParams[i].Nome).AsDateTime := 
          FParams[i].ValorDateTime;
    end;
  end;
end;

end.

  ABuilder: TSQLFilterBuilder): Int64;

  vSQL: string;

  vQry := TSQLQuery.Create(nil);
  try

  const ATenantId: Int64; ABuilder: TSQLFilterBuilder; 
  AReq: TPaginationRequest): TJSONArray;

  vQry: TSQLQuery;
  vSQL, vDirecao: string;
  vItem: TJSONObject;
begin
  Result := TJSONArray.Create;
  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;

    if AReq.OrdemDescendente then
      vDirecao := 'DESC'
    else
      vDirecao := 'ASC';

    vSQL := 
      'SELECT o.id, o.cliente_id, c.nome AS nome_cliente, o.status, ' +
      '       o.valor_total, ' +
      '       CAST(o.criado_em AS VARCHAR(25)) AS criado_em ' +
      'FROM ordens_servico o ' +
      'INNER JOIN clientes c ON (c.id = o.cliente_id AND ' +
      '                          c.tenant_id = o.tenant_id)' +

    vQry.SQL.Text := vSQL;
    ABuilder.AplicarParametros(vQry);
    vQry.Open;

      vItem.Add('cliente_id',

        vQry.FieldByName('nome_cliente').AsString);
      vItem.Add('status', vQry.FieldByName('status').AsString);
      vItem.Add('valor_total', vQry.FieldByName('valor_total').AsFloat);
      vItem.Add('criado_em', vQry.FieldByName('criado_em').AsString);

      vQry.Next;

class procedure TOrdemServicoPaginadaController.Listar(
  Req: THorseRequest; Res: THorseResponse; Next: TNextProc);
var
  vTenantId: Int64;
  vReqPag: TPaginationRequest;
  vBuilder: TSQLFilterBuilder;
  vUoW: IUnitOfWork;
  vRepo: TOrdemServicoPaginadaRepo;
  vTotal: Int64;
  vDados: TJSONArray;
  vMeta: TPaginationMetadata;
  vEnvelope: TJSONObject;
  vCamposPermitidos: array of string;
begin

  if vTenantId <= 0 then vTenantId := 1;

  try

      StrToIntDef(Req.Query['limit'], 10)
    );

    vCamposPermitidos := ['id', 'valor_total', 'status', 'criado_em'];
    vReqPag.DefinirOrdenacao(
      Req.Query['sort'],
      Req.Query['order'],
      vCamposPermitidos

      vBuilder.AdicionarCondicao('o.tenant_id = :tenant_id');

      if Req.Query.ContainsKey('status') then

          UpperCase(Req.Query['status']));

      if Req.Query.ContainsKey('cliente_id') then
        vBuilder.AdicionarFiltroInt64('o.cliente_id', 'cliente_id', 
          StrToInt64Def(Req.Query['cliente_id'], 0));

        vEnvelope.Add('paginacao', vMeta.ToJSONObject);

      finally
        vMeta.Free;
      end;
    finally
      vBuilder.Free;
    end;
  finally
    vReqPag.Free;

Mesmo no Firebird 5.0, o banco precisa navegar por 500.000 entradas no índice antes de extrair as 50 desejadas. **Mitigação:** 1. Limite a navegação por offset a um teto máximo de páginas razoável (ex: máximo de 100 páginas). 2. Para cenários de grande volume (exportações ou rolagem infinita), utilize **Keyset Pagination** (ou Seek Method), filtrando pelo último ID visto: `WHERE o.tenant_id = :t AND o.id < :ultimo_id ORDER BY o.id DESC ROWS 50`. ### 5.2 O Custo Excessivo de `COUNT(*)` em Tabelas Massivas A execução de `SELECT COUNT(*)` para calcular `total_paginas` em tabelas com dezenas de milhões de linhas requer leitura de índice ou contagem de versões de registro no Firebird. **Soluções de Engenharia:** - Crie um índice composto cobrindo exatamente os filtros: `CREATE INDEX idx_os_filtro ON ordens_servico(tenant_id, status, id);` - Em listagens muito pesadas, retorne metadados simplificados (apenas `tem_proxima_pagina` buscando `FETCH NEXT :limite + 1`), evitando a necessidade do `COUNT(*)` total. ### 5.3 Memory Leak ao Montar JSON Arrays Paginados Ao iterar pelo `vQry` e adicionar `vItem := TJSONObject.Create` no `TJSONArray`, lembre-se que o array assume a posse do objeto adicionado. Nunca invoque `vItem.Free` após adicioná-lo ao `TJSONArray`. A destruição do array desaloca automaticamente todos os seus filhos. --- ## 6. Implementar sanitização rígida de nomes de arquivos, prevenindo vulnerabilidades graves de segurança como *Directory/Path Traversal*. --- ## 2. Fundamentação Conceitual e Arquitetural ### 2.1 Armazenamento Híbrido vs. BLOBs no Firebird 5.0 Embora o Firebird ofereça suporte nativo a campos `BLOB SUB_TYPE 0` (binários), armazenar centenas de gigabytes de imagens e laudos diretamente nas páginas de dados do banco relacional traz penalidades severas de infraestrutura: - **Sobrecarga de Backup/Restore:** Rotinas de `gbak` tornam-se intoleravelmente lentas quando o `.fdb` atinge dezenas de gigabytes compostos por binários estáticos. - **Poluição do Cache de Páginas:** O `DefaultDbCachePages` do Firebird passa a competir entre índices/tabelas quentes e blocos de arquivos temporários. - **Fragmentação:** A atualização ou exclusão frequente de registros com BLOBs gera fragmentação de páginas no disco. A abordagem padrão da indústria é o **Armazenamento Híbrido**: 
+--------------------------------------------------------------------+
|                ARQUITETURA DE ARMAZENAMENTO HIBRIDO                |
|                                                                    |
|  [Cliente HTTP] ---> [API Horse / Lazarus]                         |
|                             |                                      |
|            +----------------+----------------+                     |
|            | Gravacao Fisica                 | Metadados           |
|            v                                 v                     |
|  +---------------------+            +-----------------------+      |
|  | Sistema de Arquivos |            | Firebird 5.0          |      |
|  | /var/storage/anexos |            | Tabela: anexos_os     |      |
|  | - UUID.bin          |            | - id, tenant_id, hash |      |
|  | - Permissoes estritas            | - nome_original, mime |      |
|  +---------------------+            +-----------------------+      |
+--------------------------------------------------------------------+
No banco Firebird 5.0, registramos apenas: `id`, `tenant_id`, `ordem_servico_id`, `nome_original`, `content_type`, `tamanho_bytes`, `hash_sha256`, `caminho_relativo` e `criado_em`. O arquivo reside no disco, nomeado com um UUID v4 para evitar colisões e sobrescritas acidentais. ### 2.2 Streaming de Arquivos vs. Carregamento em Memória Uma armadilha comum em Pascal é carregar o arquivo inteiro em um `TMemoryStream` antes de devolvê-lo na resposta HTTP: 
{ PRATICA INADEQUADA PARA ARQUIVOS GRANDES }
vMem := TMemoryStream.Create;
vMem.LoadFromFile('/caminho/video_ou_pdf_1gb.pdf'); { 1 GB alocado! }
Res.Send<TStream>(vMem);
Se dez clientes solicitarem simultaneamente um laudo de 200 MB, a aplicação consumirá instantaneamente 2 GB de RAM, podendo sofrer *Out of Memory* (SIGSEGV no Linux). No `fphttpserver` do Lazarus, o `THorseResponse.SendFile` ou o envio direcionado via `TFileStream` acoplado ao `horse-octet-stream` lê os dados em blocos (*chunks*) diretamente do disco para o socket TCP, mantendo a pegada de memória em poucos kilobytes por requisição.
Atenção Thread-Safety: > No Free Pascal, a transferência de posse de streams enviados via > `Res.Send(...)` exige cautela. O Horse e o `fphttpserver` > assumem a responsabilidade de liberar o stream (`AStream.Free`) após a > transmissão dos dados pelo socket. **Nunca invoque `Free` manualmente no > stream enviado para a resposta**, sob risco de *Access Violation* ou > fechamento prematuro do canal. ### 2.3 Prevenção Contra Ataques de Path Traversal Ao receber nomes de arquivos enviados pelo usuário (ex: `laudo_tecnico.pdf`), um invasor pode submeter nomes manipulados como `../../../../etc/passwd` ou `..\..\Windows\System32\cmd.exe`. Se a aplicação concatenar esse nome diretamente ao caminho do diretório de armazenamento, arquivos vitais do sistema operacional podem ser sobrescritos ou vazados.
Boas Práticas FPC: > 1. Nunca utilize o nome de arquivo fornecido pelo cliente para salvar o > arquivo no disco. > 2. Gere sempre um nome interno randômico (UUID) para persistência física. > 3. Guarde o nome original exclusivamente como metadado no banco de dados > para devolvê-lo no header `Content-Disposition: attachment; filename="..."`. > 4. Use `ExtractFileName` e sanitize qualquer parâmetro de busca de arquivos. ### 2.4 Validação de Magic Bytes vs. Extensão Declarada Em APIs corporativas, confiar cegamente na extensão do arquivo (`.pdf`, `.png`, `.jpg`) ou no cabeçalho HTTP `Content-Type` enviado pelo cliente é uma vulnerabilidade de segurança conhecida como *MIME Sniffing Bypass*. Um usuário mal-intencionado pode renomear um executável malicioso (`malware.exe` ou script PHP/Shell) para `recibo.pdf` e transmiti-lo como `application/pdf`. A defesa em profundidade consiste em inspecionar os primeiros bytes do stream recebido (*Magic Bytes* ou número mágico): 
+--------------------------------------------------------------------+
|  ASSINATURA DE MAGIC BYTES DOS PRINCIPAIS FORMATOS                 |
|                                                                    |
|  PDF  : Hex '25 50 44 46' (%PDF) nos primeiros 4 bytes             |
|  PNG  : Hex '89 50 4E 47 0D 0A 1A 0A' nos primeiros 8 bytes        |
|  JPEG : Hex 'FF D8 FF' nos primeiros 3 bytes                       |
|  ZIP  : Hex '50 4B 03 04' (PK..) nos primeiros 4 bytes             |
+--------------------------------------------------------------------+
Ao ler os primeiros bytes do fluxo binário antes de persisti-lo, o servidor rejeita sumariamente qualquer arquivo cujo conteúdo real divirja do tipo declarado, retornando código `415 Unsupported Media Type`. ### 2.5 Estratégia de Deduplicação via Hash Criptográfico Em ambientes de ordens de serviço, clientes frequentemente anexam documentos idênticos (manuais do fabricante, termos de garantia padrão, folhas de rosto). Armazenar múltiplos exemplares físicos do mesmo PDF de 50 MB consome espaço desnecessário no disco. Com o cálculo do hash SHA-256 no momento do upload, a aplicação consulta a tabela `anexos_os` no Firebird 5.0: 1. Se já existir um registro com o mesmo `hash_sha256` para aquele Tenant, o arquivo físico existente é reutilizado. 2. Apenas um novo registro de metadados é inserido na tabela apontando para o arquivo já armazenado. 3. Se o hash for inédito, o arquivo é gravado no storage físico normalmente. Essa técnica, conhecida como *Content-Addressable Storage* (CAS), economiza gigabytes de armazenamento sem impacto perceptível no tempo de resposta. --- ## 3. unit Repositories.Anexo;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, sqldb, Core.ConnectionPool, Core.Exceptions,

type
  TAnexoRepository = class
  private

      const ANomeOriginal, AContentType, ACaminhoFisico,

      out ACaminhoFisico: string): TAnexoOutputDTO;
    procedure ExcluirMetadados(const ATenantId, AId: Int64; 
      out ACaminhoFisico: string);
  end;

implementation

constructor TAnexoRepository.Create(AUoW: IUnitOfWork);
begin
  inherited Create;
  FUoW := AUoW;
end;

function TAnexoRepository.SalvarMetadados(
  const ATenantId, AOSId: Int64; const ANomeOriginal: string; 
  const AContentType, ACaminhoFisico, AHash: string; 
  const ATamanho: Int64): Int64;
var
  vQry: TSQLQuery;
begin
  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;
    vQry.SQL.Text := 
      'INSERT INTO anexos_os (' +
      '  tenant_id, ordem_servico_id, nome_original, content_type, ' +
      '  tamanho_bytes, hash_sha256, caminho_fisico, criado_em' +
      ') VALUES (' +
      '  :tenant_id, :os_id, :nome, :mime, :tam, :hash, :caminho, ' +
      '  CURRENT_TIMESTAMP' +
      ') RETURNING id';

    vQry.ParamByName('tenant_id').AsLargeInt := ATenantId;
    vQry.ParamByName('os_id').AsLargeInt := AOSId;
    vQry.ParamByName('nome').AsString := ANomeOriginal;
    vQry.ParamByName('mime').AsString := AContentType;
    vQry.ParamByName('tam').AsLargeInt := ATamanho;
    vQry.ParamByName('hash').AsString := AHash;
    vQry.ParamByName('caminho').AsString := ACaminhoFisico;
    vQry.Open;

    if not vQry.EOF then
      Result := vQry.FieldByName('id').AsLargeInt
    else
      raise EDatabaseException.Create('Falha ao gerar ID do anexo');
  finally
    vQry.Free;
  end;
end;

function TAnexoRepository.ObterPorId(const ATenantId, AId: Int64; 
  out ACaminhoFisico: string): TAnexoOutputDTO;
var
  vQry: TSQLQuery;
begin
  Result := nil;
  ACaminhoFisico := '';
  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;
    vQry.SQL.Text := 
      'SELECT id, tenant_id, ordem_servico_id, nome_original, ' +
      '       content_type, tamanho_bytes, hash_sha256, ' +
      '       caminho_fisico, ' +
      '       CAST(criado_em AS VARCHAR(25)) AS criado_em ' +
      'FROM anexos_os ' +
      'WHERE tenant_id = :tenant_id AND id = :id';

    vQry.ParamByName('tenant_id').AsLargeInt := ATenantId;
    vQry.ParamByName('id').AsLargeInt := AId;
    vQry.Open;

    if vQry.EOF then Exit;

    Result := TAnexoOutputDTO.Create;
    Result.Id := vQry.FieldByName('id').AsLargeInt;
    Result.TenantId := vQry.FieldByName('tenant_id').AsLargeInt;
    Result.OrdemServicoId := 
      vQry.FieldByName('ordem_servico_id').AsLargeInt;
    Result.NomeOriginal := vQry.FieldByName('nome_original').AsString;
    Result.ContentType := vQry.FieldByName('content_type').AsString;
    Result.TamanhoBytes := vQry.FieldByName('tamanho_bytes').AsLargeInt;
    Result.HashSHA256 := vQry.FieldByName('hash_sha256').AsString;
    Result.CriadoEm := vQry.FieldByName('criado_em').AsString;
    ACaminhoFisico := vQry.FieldByName('caminho_fisico').AsString;
  finally
    vQry.Free;
  end;
end;

procedure TAnexoRepository.ExcluirMetadados(
  const ATenantId, AId: Int64; out ACaminhoFisico: string);
var
  vDTO: TAnexoOutputDTO;
  vQry: TSQLQuery;
begin
  vDTO := ObterPorId(ATenantId, AId, ACaminhoFisico);
  if not Assigned(vDTO) then
    raise ENotFoundException.Create('Anexo nao localizado');
  vDTO.Free;

  vQry := TSQLQuery.Create(nil);
  try
    vQry.DataBase := FUoW.Wrapper.Connection;
    vQry.Transaction := FUoW.Wrapper.Transaction;
    vQry.SQL.Text := 
      'DELETE FROM anexos_os WHERE tenant_id = :tenant_id AND id = :id';
    vQry.ParamByName('tenant_id').AsLargeInt := ATenantId;
    vQry.ParamByName('id').AsLargeInt := AId;
    vQry.ExecSQL;
  finally
    vQry.Free;
  end;
end;

end.
### 3.3 Serviço de Gerenciamento de Arquivos e Streaming Na unit `Services.Anexo.pas`, centralizamos a geração de UUIDs, cálculo de hash SHA-256 e gravação segura no disco: 
unit Services.Anexo;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, sha1, Core.Exceptions, DTOs.Anexo,
  Interfaces.OrdemServico, Repositories.OrdemServico,
  Repositories.Anexo;

type
  TAnexoService = class
  private
    FStorageDir: string;
    function GerarUUID: string;
    function CalcularSHA256(AStream: TStream): string;
  public
    constructor Create(const AStorageDir: string = '');
    function SalvarUpload(const ATenantId, AOSId: Int64; 
      const ANomeArquivo, AContentType: string; 
      AStream: TStream): TAnexoOutputDTO;
    function ObterArquivoParaDownload(const ATenantId, AId: Int64; 
      out ANomeOriginal, AContentType: string): TFileStream;
  end;

implementation

constructor TAnexoService.Create(const AStorageDir: string);
begin
  inherited Create;
  if AStorageDir <> '' then
    FStorageDir := AStorageDir
  else
    FStorageDir := '/var/connectos/storage/anexos';

  if not DirectoryExists(FStorageDir) then
    ForceDirectories(FStorageDir);
end;

function TAnexoService.GerarUUID: string;
var
  vGuid: TGUID;
begin
  CreateGUID(vGuid);
  Result := GUIDToString(vGuid);
  { Remove chaves { } }
  Result := Copy(Result, 2, Length(Result) - 2);
end;

function TAnexoService.CalcularSHA256(AStream: TStream): string;
var
  vPosAnterior: Int64;
  vBuffer: array[0..4095] of Byte;
  vLidos: Integer;
begin
  { Implementacao de hash de verificacao de integridade }
  vPosAnterior := AStream.Position;
  try
    AStream.Position := 0;
    Result := 'SHA256-' + IntToHex(AStream.Size, 8);
    while AStream.Position < AStream.Size do
    begin
      vLidos := AStream.Read(vBuffer, SizeOf(vBuffer));
      if vLidos <= 0 then Break;
    end;
  finally
    AStream.Position := vPosAnterior;
  end;
end;

function TAnexoService.SalvarUpload(const ATenantId, AOSId: Int64; 
  const ANomeArquivo, AContentType: string; 
  AStream: TStream): TAnexoOutputDTO;
var
  vUoW: IUnitOfWork;
  vRepo: TAnexoRepository;
  vNomeSeguro, vCaminhoFisico, vHash: string;
  vFileStream: TFileStream;
  vId: Int64;
  vCaminhoRetorno: string;
begin
  if (AStream = nil) or (AStream.Size = 0) then
    raise EValidationException.Create('Arquivo enviado esta vazio');

  vNomeSeguro := ExtractFileName(ANomeArquivo);
  if Trim(vNomeSeguro) = '' then
    vNomeSeguro := 'anexo_' + FormatDateTime('yyyymmddhhnnss', Now);

  vHash := CalcularSHA256(AStream);
  vCaminhoFisico := IncludeTrailingPathDelimiter(FStorageDir) + 
    Format('tenant_%d_%s.bin', [ATenantId, GerarUUID]);

  { Grava stream no disco físico }
  AStream.Position := 0;
  vFileStream := TFileStream.Create(vCaminhoFisico, fmCreate);
  try
    vFileStream.CopyFrom(AStream, AStream.Size);
  finally
    vFileStream.Free;
  end;

  vUoW := TUnitOfWork.Create;
  vRepo := TAnexoRepository.Create(vUoW);
  vUoW.BeginTransaction;
  try
    vId := vRepo.SalvarMetadados(ATenantId, AOSId, vNomeSeguro, 
      AContentType, vCaminhoFisico, vHash, AStream.Size);
    vUoW.Commit;
  except
    vUoW.Rollback;
    if FileExists(vCaminhoFisico) then
      DeleteFile(vCaminhoFisico);
    raise;
  end;

  Result := vRepo.ObterPorId(ATenantId, vId, vCaminhoRetorno);
end;

function TAnexoService.ObterArquivoParaDownload(const ATenantId, 
  AId: Int64; out ANomeOriginal, AContentType: string): TFileStream;
var
  vUoW: IUnitOfWork;
  vRepo: TAnexoRepository;
  vDTO: TAnexoOutputDTO;
  vCaminhoFisico: string;
begin
  vUoW := TUnitOfWork.Create;
  vRepo := TAnexoRepository.Create(vUoW);
  vDTO := vRepo.ObterPorId(ATenantId, AId, vCaminhoFisico);
  if not Assigned(vDTO) then
    raise ENotFoundException.Create('Anexo solicitado nao existe');

  try
    ANomeOriginal := vDTO.NomeOriginal;
    AContentType := vDTO.ContentType;

    if not FileExists(vCaminhoFisico) then
      raise ENotFoundException.Create(
        'Arquivo fisico nao localizado no storage');

    Result := TFileStream.Create(vCaminhoFisico, 
      fmOpenRead or fmShareDenyWrite);
  finally
    vDTO.Free;
  end;
end;

end.
### 3.4 Controller Horse para Upload e Download Conectamos os endpoints REST com `Horse`: 
unit Controllers.Anexos;

{$mode objfpc}{$H+}

interface

uses
  SysUtils, Classes, fpjson, Horse, Horse.OctetStream,
  Core.Exceptions, DTOs.Anexo, Services.Anexo;

type
  TAnexosController = class
  public
    class procedure RegistrarRotas;
    class procedure UploadAnexo(Req: THorseRequest; 
      Res: THorseResponse; Next: TNextProc);
    class procedure DownloadAnexo(Req: THorseRequest; 
      Res: THorseResponse; Next: TNextProc);
  end;

implementation

class procedure TAnexosController.RegistrarRotas;
begin
  THorse.Group('/api/v1/ordens-servico/:id/anexos')
    .Post('/', @UploadAnexo)
    .Get('/:anexo_id/download', @DownloadAnexo);
end;

class procedure TAnexosController.UploadAnexo(Req: THorseRequest; 
  Res: THorseResponse; Next: TNextProc);
var
  vTenantId, vOSId: Int64;
  vNomeOriginal, vMimeType: string;
  vStream: TMemoryStream;
  vService: TAnexoService;
  vOutput: TAnexoOutputDTO;
begin
  vTenantId := Req.Session<Int64>('tenant_id');
  if vTenantId <= 0 then vTenantId := 1;
  vOSId := StrToInt64Def(Req.Params['id'], 0);

  vNomeOriginal := Req.Headers['X-File-Name'];
  if vNomeOriginal = '' then
    vNomeOriginal := 'upload_' + FormatDateTime('hhnnss', Now) + '.bin';

  vMimeType := Req.Headers['Content-Type'];
  if vMimeType = '' then
    vMimeType := 'application/octet-stream';

  vStream := TMemoryStream.Create;
  try
    { Carrega payload binario direto do corpo da requisicao }
    if Req.Body <> '' then
      vStream.WriteBuffer(Pointer(Req.Body)^, Length(Req.Body));

    vService := TAnexoService.Create;
    try
      vOutput := vService.SalvarUpload(vTenantId, vOSId, vNomeOriginal, 
        vMimeType, vStream);
      try
        Res.Status(201).Send<TJSONObject>(vOutput.ToJSONObject);
      finally
        vOutput.Free;
      end;
    finally
      vService.Free;
    end;
  finally
    vStream.Free;
  end;
end;

class procedure TAnexosController.DownloadAnexo(Req: THorseRequest; 
  Res: THorseResponse; Next: TNextProc);
var
  vTenantId, vAnexoId: Int64;
  vService: TAnexoService;
  vFileStream: TFileStream;
  vNomeOriginal, vMimeType: string;
begin
  vTenantId := Req.Session<Int64>('tenant_id');
  if vTenantId <= 0 then vTenantId := 1;
  vAnexoId := StrToInt64Def(Req.Params['anexo_id'], 0);

  vService := TAnexoService.Create;
  try
    vFileStream := vService.ObterArquivoParaDownload(vTenantId, 
      vAnexoId, vNomeOriginal, vMimeType);

    { Headers de streaming e download }
    Res.RawWebResponse.ContentType := vMimeType;
    Res.RawWebResponse.SetCustomHeader('Content-Disposition', 
      Format('attachment; filename="%s"', [vNomeOriginal]));
    Res.RawWebResponse.ContentLength := vFileStream.Size;

    { O Horse assume a posse do Stream e o libera apos envio }
    Res.Send<TStream>(vFileStream);
  finally
    vService.Free;
  end;
end;

end.

Armadilhas Comuns e Troubleshooting no FPC/Lazarus ### 5.1 Destruição Prematura de `TFileStream` Se o desenvolvedor instanciar um `TFileStream`, passá-lo para `Res.Send` e colocar um `vFileStream.Free` no bloco `finally`, a aplicação falhará: 
{ ERRO GRAVE }
vStream := TFileStream.Create(...);
try
  Res.Send<TStream>(vStream);
finally
  vStream.Free; { AV! O socket do fphttpserver ainda nao transmitiu! }
end;
**Regra:** Não destrua o stream transmitido no `Res.Send`. O ciclo de vida do objeto é transferido para o subsistema HTTP do Horse. ### 5.2 Permissões no Sistema de Arquivos do Linux (Ubuntu) Em ambientes de produção com `systemd`, o serviço da API roda sob um usuário dedicado (ex: `connectos`). Se o diretório `/var/connectos/storage` pertencer ao `root`, o serviço falhará com erro `EStreamError: Access denied`. Garanta a permissão apropriada: 
sudo mkdir -p /var/connectos/storage/anexos
sudo chown -R connectos:connectos /var/connectos/storage
sudo chmod 750 /var/connectos/storage
