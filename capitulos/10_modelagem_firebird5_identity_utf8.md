## 2. FUNDAMENTAÇÃO CONCEITUAL E ARQUITETURAL

O ecossistema Pascal e o banco de dados **Firebird** compartilham uma simbiose histórica marcada por estabilidade operacional inabalável, baixíssimo consumo de hardware e custo zero de licenciamento. Enquanto bancos como Oracle e Microsoft SQL Server demandam servidores colossais e licenças proibitivas, e engines como MySQL exigem afinações complexas de parâmetros de storage, o Firebird sempre se destacou pela resiliência (*zero-admin*).

Contudo, a chegada da versão **Firebird 5.0** representou um salto quântico de engenharia, transformando o SGBD em uma das opções mais velozes e modernas do mercado para APIs de alta concorrência.

Entre as principais melhorias do Firebird 5.0 para APIs RESTful, destacam-se:
- **Execução Paralela de Tarefas (Parallel Workers):** O motor agora é capaz de paralelizar operações internas de varredura e ordenação, além de rotinas concorrentes de varredura de índices.
- **Cache de Instruções SQL Compiladas (Compiled Statements Cache):** Queries parametrizadas disparadas frequentemente por serviços web têm seus planos de execução (PLAN) e código compilado preservados na memória compartilhada do servidor, reduzindo o tempo de CPU no parsing de SQL a zero em chamadas repetidas.
- **Otimizador Aprimorado para Paginação:** A engine foi completamente remodelada para executar a cláusula `OFFSET ... FETCH NEXT ... ROWS ONLY` sem precisar materializar o conjunto completo de dados em disco.

### O Conjunto de Caracteres UTF8 e a Eliminação da Falha de Transliteração

A especificação do protocolo HTTP e do formato JSON (RFC 8259) determina que o tráfego de dados na web moderna deve ser estritamente codificado em **UTF-8**.

Nas versões antigas do Firebird (1.5 e 2.x), era comum desenvolvedores criarem bancos com conjuntos legados de caracteres, como `WIN1252` ou `ISO8859_1`. Quando uma API em Horse recebia caracteres acentuados (como *"Manutenção e Diagnóstico"*), caracteres com emojis ou símbolos monetários (`R$`, `€`), e tentava gravá-los no banco sem correspondência direta de byte, o driver de banco lançava a exceção clássica:

```text
GDS Code: 335544569 -
Cannot transliterate character between character sets
```

No Firebird 5.0, a regra de ouro para qualquer API RESTful corporativa é unificar toda a cadeia em UTF-8:
1. **No Banco Físico:** Criação do banco com `DEFAULT CHARACTER SET UTF8`.
2. **Nas Conexões de Rede:** Configuração obrigatória do parâmetro `lc_ctype=UTF8` na string de conexão do cliente.
3. **Na Camada Pascal:** Compilação do código com `{$H+}` (AnsiString/UTF8 dinâmica nativa).

Com esses três pilares alinhados, a transliteração torna-se puramente transparente: zero perdas de acentuação e zero erros de charset.

### Colunas IDENTITY: Modernidade sem Triggers Artesanais

No Firebird clássico, a criação de chaves primárias autoincrementais exigia dois artefatos manuais por tabela:
1. Uma Sequence/Generator dedicada: `CREATE SEQUENCE gen_clientes_id;`
2. Uma Trigger *Before Insert* obrigatória:
   ```sql
   /* MODELO LEGADO E OBSOLETO - NÃO UTILIZE NO FIREBIRD 5 */
   CREATE TRIGGER trg_clientes_bi FOR clientes
   BEFORE INSERT AS
   BEGIN
     IF (NEW.id IS NULL) THEN
       NEW.id = NEXT VALUE FOR gen_clientes_id;
   END
   ```

Essa abordagem antiga carregava deficiências graves: poluição do catálogo de metadados, lentidão em operações de inserção em massa (*bulk insert*) e necessidade de transações adicionais para capturar o ID gerado via `GEN_ID(gen_clientes_id, 0)`.

A partir das versões modernas e consolidado com maestria no **Firebird 5.0**, adotamos a sintaxe nativa padrão **ANSI SQL:2008**:

```sql
CREATE TABLE clientes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ...
);
```

Vantagens da coluna `IDENTITY`:
- **Semântica `BY DEFAULT`:** Se o cliente não informar o ID no comando `INSERT`, o motor do Firebird gera automaticamente o próximo valor da sequência interna. Se um processo de replicação ou migração de dados informar um ID explicitamente, o banco respeita o valor informado.
- **Tipagem em `BIGINT` (64 bits):** Chaves primárias devem utilizar inteiros de 64 bits (`Int64` no Pascal). O limite de um inteiro de 32 bits (`INTEGER` - 2,14 bilhões) é facilmente superado em tabelas volumosas de ordens de serviço, itens ou logs de auditoria em ambientes SaaS.
- **Desempenho Extremo:** A geração do valor ocorre diretamente no núcleo C++ do motor do banco, sem o overhead de disparar o interpretador PSQL para executar triggers.

### A Cláusula RETURNING: Atomicidade em uma Única Viagem de Rede

Quando uma API executa um comando `POST` para criar um cliente, o protocolo HTTP 201 Created exige que a resposta informe o identificador gerado e emita o cabeçalho `Location: /api/v1/clientes/:id`.

No passado, os desenvolvedores executavam o `INSERT`, fechavam a query e disparavam uma segunda consulta (`SELECT FIRST 1 id FROM ... ORDER BY id DESC`) para descobrir qual ID havia sido atribuído. Essa prática gerava condições de corrida (*race conditions*) perigosas em ambientes concorrentes e dobrava a latência de rede.

No Firebird 5.0, a cláusula **`RETURNING`** resolve esse problema atomicamente:

```sql
INSERT INTO clientes (tenant_id, nome_razao, cpf_cnpj)
VALUES (1, 'Oficina Mecanica Central', '11222333000199')
RETURNING id, created_at;
```

O comando executa a inserção e devolve imediatamente o ID gerado pelo `IDENTITY` e o timestamp gerado pelo servidor em um único pacote TCP, garantindo velocidade máxima e consistência transacional absoluta.

### Modelagem Física Multi-Tenant: A Estratégia de Banco Compartilhado

Em plataformas de software como serviço (SaaS), existem três modelos clássicos de isolamento de dados:
1. *Banco por Inquilino (Database per Tenant):* Um arquivo `.fdb` físico separado para cada cliente. Oferece isolamento total, mas inviabiliza a manutenção quando a base atinge centenas de inquilinos (complexidade extrema de migrações DDL e saturação de pools).
2. *Schema por Inquilino (Schema per Tenant):* Suportado por bancos como PostgreSQL, mas inexistente no Firebird.
3. *Banco Compartilhado com Coluna Discriminadora (Shared Database, Shared Schema):* Todas as empresas compartilham o mesmo banco de dados físico e as mesmas tabelas, sendo rigorosamente isoladas por uma coluna mandatória: **`tenant_id`**.

A abordagem de **Banco Compartilhado** é a mais eficiente, econômica e escalável para a nossa **ConnectOSApi**.

```
+--------------------------------------------------------------------+
|                  TABELA COMPARTILHADA: CLIENTES                    |
+----+-----------+------------------------------+--------------------+
| id | tenant_id | nome_razao                   | cpf_cnpj           |
+----+-----------+------------------------------+--------------------+
|  1 |     1     | Conect Solutions TI LTDA     | 12345678000199     |
|  2 |     1     | Mecanica Brasil Express      | 98765432000100     |
|  3 |     2     | Posto Alvorada Combustíveis  | 55666777000122     |
|  4 |     2     | Transportes Sul-Norte LTDA   | 33444555000133     |
+----+-----------+------------------------------+--------------------+
```

#### A Importância dos Índices Compostos Iniciados por tenant_id

Para que a arquitetura Multi-Tenant com banco compartilhado não sofra degradação de desempenho à medida que a base cresce, todos os índices e restrições de unicidade devem ser obrigatoriamente compostos, tendo o campo **`tenant_id` como a primeira coluna do índice**:

```sql
/* INDICE COMPOSTO DE ALTA PERFORMANCE */
CREATE INDEX idx_clientes_tenant_nome 
  ON clientes(tenant_id, nome_razao);
CREATE INDEX idx_os_tenant_status ON ordens_servico(tenant_id, status);

/* CHAVE UNICA POR INQUILINO (DOIS TENANTS PODEM TER O MESMO CNPJ) */
CONSTRAINT unq_clientes_tenant_doc UNIQUE (tenant_id, cpf_cnpj);
```

Se o índice fosse criado apenas sobre `nome_razao`, o motor do banco teria que varrer o índice inteiro para depois filtrar por tenant. Iniciando o índice por `tenant_id`, o otimizador do Firebird pula instantaneamente para a fatia de dados pertencente àquele inquilino específico (*Index Seek*), ignorando completamente os milhões de registros dos outros clientes da plataforma.

### Passo 2: Criando o Banco de Dados Físico com Utilitários do Firebird

Para testar a infraestrutura em ambiente de desenvolvimento, utilizaremos o console de linha de comando nativo do Firebird: o **`isql`** (ou `isql-fb` no Linux).

#### Procedimento no Linux (Ubuntu 24.04 LTS):

Abra o terminal e execute:

```bash
# Acesso ao utilitario isql do Firebird
sudo isql-fb

# Criacao do banco fisico com Charset UTF8 e Pagina de 16 KB
CREATE DATABASE '/var/lib/firebird/data/connect_os.fdb'
  PAGE_SIZE 16384
  USER 'SYSDBA' PASSWORD 'masterkey'
  DEFAULT CHARACTER SET UTF8;

# Execucao do script de metadados
INPUT /caminho/do/projeto/database/schema_fb5.sql;

# Confirmacao de saida
QUIT;
```

#### Procedimento no Windows 11:

Abra o Prompt de Comando ou PowerShell:

```cmd
:: Navega ate a pasta binaria de instalacao do Firebird 5.0
cd "C:\Program Files\Firebird\Firebird_5_0"

:: Executa o isql criando o banco de dados
isql -u SYSDBA -p masterkey

SQL> CREATE DATABASE 'C:\Projetos Antigrtavity\connect_os.fdb'

CON> DEFAULT CHARACTER SET UTF8;

SQL> INPUT database/schema_fb5.sql;
SQL> COMMIT;
SQL> QUIT;
```

> **Boas Práticas FPC:**  
> A escolha de `PAGE_SIZE 16384` (16 Kilobytes) é a mais indicada para servidores modernos de 64 bits operando em discos SSD/NVMe. Tamanhos de página maiores reduzem a profundidade das árvores de índices B-Tree, permitindo que o Firebird localize registros com menos operações de leitura de I/O em disco.

## 5. ARMADILHAS COMUNS E TROUBLESHOOTING NO FPC/LAZARUS

---

### Armadilha 1: Incompatibilidade de Bits da Biblioteca fbclient (32 vs 64 bits)

**Sintoma:** Ao compilar e executar uma aplicação Lazarus que conecta ao Firebird, o programa aborta com a mensagem:

```text
Can not load default Firebird clients ("fbclient.dll" or "gds32.dll"). 
Check your installation!
```

**Causa Raiz:** O executável em Pascal foi compilado como binário de 64 bits (`x86_64`), mas está tentando carregar uma biblioteca cliente `fbclient.dll` de 32 bits herdada de instalações antigas do Delphi, ou vice-versa.

**Solução:** Garanta que a arquitetura do executável corresponda estritamente à arquitetura da DLL/SO. No Lazarus 64-bit para Windows, utilize a `fbclient.dll` da pasta `Firebird_5_0` de 64 bits. No Linux Ubuntu x86_64, instale o pacote nativo de 64 bits:

```bash
sudo apt install -y libfbclient2
```

---

### Armadilha 2: Sincronização Desalinhada de Colunas IDENTITY

**Sintoma:** Ao importar registros legados em massa com IDs explícitos (ex: `INSERT INTO clientes (id, ...) VALUES (500, ...)`), a próxima inserção automática que omite o ID falha com violação de chave primária duplicada!

**Causa Raiz:** Ao inserir manualmente valores maiores na coluna IDENTITY, a sequência interna associada pelo Firebird não é avançada automaticamente se o comando não reajustar o gerador.

**Solução:** Após operações de importação manual de dados legados, reajuste o contador da sequência interna da tabela IDENTITY para o maior valor existente:

```sql
ALTER TABLE clientes ALTER COLUMN id RESTART WITH 501;
```

---

### Armadilha 3: Bloqueio Transacional por Falta de Commit em Ferramentas de Apoio

**Sintoma:** A API em Horse tenta atualizar um registro no Firebird e a requisição congela por 30 segundos até estourar por *timeout* (*Lock conflict on no wait transaction*).

**Causa Raiz:** O desenvolvedor abriu o DBeaver, FlameRobin ou `isql`, executou um `UPDATE` ou `SELECT` para conferir dados e esqueceu de fechar ou comitar a transação na ferramenta gráfica, retendo um bloqueio exclusivo sobre o registro.

**Solução:** No Firebird, transações ativas seguram bloqueios de versão de registro. Sempre configure ferramentas de administração com commit automático (*Auto-Commit*) ou lembre-se de executar `COMMIT;` após qualquer consulta interativa.

## 6. RESUMO EXECUTIVO E CHECKLIST DE REVISÃO

### Tabela de Comparação: Firebird Legado vs. Firebird 5.0 Moderno

| Recurso / Paradigma | Firebird Clássico (1.5 a 2.5) | Firebird 5.0 Moderno |
| :--- | :--- | :--- |
| **Chave Primária** | `INTEGER` com Generators e Triggers | `BIGINT GENERATED BY DEFAULT AS IDENTITY`|
| **Captura de ID** | Chamada extra `GEN_ID(gen, 0)` | Cláusula atômica `RETURNING id` |
| **Encoding Padrão**| `NONE`, `WIN1252` ou `ISO8859_1` | `UTF8` Universal nativo em toda a stack |
| **Paginação** | `FIRST ... SKIP ...` lento em heap | `OFFSET ... FETCH NEXT ... ROWS ONLY` |
| **Processamento** | Single-thread ou Multi-process | Multi-thread com paralelismo nativo |
| **Plano de Execução**| Parsing e compilação a cada query | Cache compartilhado de statements |
